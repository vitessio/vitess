# MySQL Group Replication as a first-class replication mode

Status: prototype / RFC. Related: [#18648](https://github.com/vitessio/vitess/issues/18648) (Uber's "consensus" RFC), [#13300](https://github.com/vitessio/vitess/issues/13300) (removal of the experimental VTGR).

## Goals

- A shard can replicate with MySQL Group Replication (GR) in single-primary mode instead of asynchronous replication plus semi-sync, selected with a **durability policy**, just like `semi_sync` or `cross_cell` today.
- Every existing operational tool keeps working with the same semantics: `PlannedReparentShard`, `EmergencyReparentShard`, VTOrc, backups/restores, `vtctldclient GetFullStatus`, vtgate buffering. No second orchestrator.
- An existing semi-sync shard can be converted to GR **online**, one tablet at a time, with durability preserved at every step, and converted back.
- GR's guarantees are used, not re-implemented: the group fences a partitioned primary, elects a new primary without an external agent, and never lets a member diverge.

## Non-goals

- Multi-primary mode. Vitess routes writes to a single primary; multi-primary adds certification conflicts for no gain.
- InnoDB Cluster / MySQL Shell / MySQL Router. Vitess already provides routing (vtgate) and topology (topo).
- More than 9 voting members per shard (a MySQL limit). Additional tablets replicate asynchronously from the group.

## Why VTGR failed, and what is different

VTGR was a separate daemon per tablet host that talked MySQL protocol, duplicated VTOrc's control loop, turned every replication RPC into a silent no-op (the `MysqlGR` flavor), and left PRS/ERS semantics undefined. Nobody ran it in production.

This design instead makes GR a **replication mode inside the existing control plane**:

| Concern | Where it lives | Mechanism |
|---|---|---|
| Choose GR | keyspace durability policy; a shard's own policy while its keyspace is migrated | `group_replication_cross_cell` |
| MySQL primitives | `go/mysql`, `mysqlctl.MysqlDaemon` | `GroupReplicationStatus`, `ConfigureGroupReplication`, `StartGroupReplication`, `StopGroupReplication`, `SetGroupReplicationPrimary` |
| Observability | `FullStatus.group_replication_status` | VTOrc, `GetFullStatus` |
| Membership lifecycle | vttablet (tabletmanager) | tablet derives its GR config from topo; RPCs `StartGroupReplication`/`StopGroupReplication` |
| Topology follows the group | vttablet reconcile loop + VTOrc | tablet promotes/demotes its own record when its group role changes |
| Planned switchover | PRS | same orchestration; tablet implements `PromoteReplica` with `group_replication_set_as_primary()` |
| Unplanned failover | the group itself + ERS/VTOrc | group elects; Vitess reconciles topo; ERS handles loss of quorum only when explicitly asked |
| Migration | `vtctldclient MigrateReplicationMode` (reparentutil) | ordered, idempotent, shard-locked steps |

## Semi-sync vs Group Replication (summary)

See the research notes linked from the PR for sources; the points that shape the design:

- **Durability.** Lossless semi-sync (AFTER_SYNC) returns to the client after *one* eligible replica has written the event to its relay log. GR returns after a *majority* of the group has *accepted* the transaction in XCom, the group's Paxos, and the primary has certified it. An acceptor holds the message in memory; it only receives the transaction, into its relay log, once it learns XCom's decision, which may not have reached it yet. Neither mode waits for the transaction to be applied on another server. With one member per cell in three cells, both cost roughly one round trip to the nearest other cell; `cross_cell` semi-sync and a 3-cell group have similar commit latency. See "What an acknowledged commit guarantees" below.
- **Fencing.** Semi-sync has no membership: a partitioned primary keeps its binlog, and after an ERS its unacknowledged transactions become errant GTIDs; Vitess must fence it (`super_read_only`, tablet type, errant GTID detection). A GR primary that loses its majority cannot commit; its transactions block and are never certified, so it cannot diverge. `group_replication_unreachable_majority_timeout` bounds how long it blocks.
- **Election.** Semi-sync needs an external agent (VTOrc) to promote. GR elects on its own after a fixed 5s detection period plus the expulsion delay. On MySQL 8.4.11 that delay measured 1s with `group_replication_member_expel_timeout=0`, but 16s for any value from 1 to 10s. It chooses by lowest version, then highest `group_replication_member_weight`, then lowest `server_uuid`. Vitess maps promotion rules onto member weights so that the group's choice matches Vitess's preferences.
- **Loss of majority.** Semi-sync keeps running as long as one eligible acker remains. GR stops accepting writes; only `group_replication_force_members` (an operator decision, split-brain risk) unblocks it. Once the members have left the group, VTOrc bootstraps it again only when every voter is reachable, or once the operator deleted the tablet record of a voter that is gone for good (see "What an acknowledged commit guarantees"). This is the main availability trade-off.
- **Behaviour changes users see.** Every table needs a primary key; transactions above `group_replication_transaction_size_limit` (~143MB) are rolled back; one slow secondary throttles the primary through flow control; GTIDs use the group UUID instead of the server UUID.

### What an acknowledged commit guarantees

A group acknowledges a commit once a majority of its members *accepted* it in XCom. That is not the same as a majority having *received* it, let alone stored or applied it. The lab verified this on MySQL 8.4.11 (`doc/failover-audit/GroupReplication.md`, "Majority bootstrap analysis", runs L1, L1b and L4: a group of two, the primary's XCom traffic delayed by 20ms, then cut). Each time, the primary had committed transactions that the other member, whose acceptance the primary needed, had neither received nor executed (7 transactions in each run).

- **While the group keeps its majority,** XCom delivers every decided transaction to every member that stays in the group, including the members that only accepted it. A failover elected by the group loses nothing, and `BEFORE_ON_PRIMARY_FAILOVER` makes the new primary apply it before it serves.
- **Once the group has lost its majority** and its members have left it, an acceptor discards what it only held in memory. A transaction that no other member had received yet then exists only in the old primary's binlog: on a single server, although a majority acknowledged it. A member that left with a received but unapplied backlog keeps it in its relay log, and applies it when it is bootstrapped (L4); but a restart with `relay_log_recovery=ON`, which Vitess sets, discards that backlog (L2, L3, and the G11k chaos scenario).
- **Semi-sync** offers a comparable guarantee by a different path. Its acknowledgement means that one replica has written the transaction to its relay log, not that it applied or synced it; the same `relay_log_recovery=ON` discards it when that replica restarts (§2 of the failover audit, S11). After the primary fails, ERS promotes the most advanced replica, so a semi-sync transaction is lost only if its acker lost its relay log too. GR adds a majority, but in memory: losing the majority, without losing any server, is enough to leave an acknowledged transaction on the old primary alone.

This is why VTOrc bootstraps a group that lost its majority only when **every voter**, the old primary included, is reachable, and only on a voter that holds every transaction any voter executed or received, and only once that voter has them all in its binlog (`GroupNotBootstrapped`, see "The bootstrap candidate" below). The voters that remained, even a majority of them, cannot tell whether the old primary holds acknowledged transactions they lack: a bootstrap without it would discard them, and its binlog would then hold errant transactions. A bootstrap from a majority of the voters was analyzed and rejected for this reason (see "Majority bootstrap analysis" in the audit). The cost is availability: the shard has no primary until the last voter is back.

**When a voter is gone for good.** A group that lost its majority while one of its voters died for good, its host lost, stays down: VTOrc waits for every voter. The operator unblocks it by deleting that voter's tablet record (`vtctldclient DeleteTablets`): VTOrc then removes the voter from the list while no group runs (RemoveVoterNoGroup, see "Voters"), and bootstraps the group from the remaining voters, over every transaction they executed or received. What only the deleted voter held is lost: a transaction that the old primary acknowledged while it was, with the deleted voter, the majority that accepted it, and that no remaining voter received. Deleting the record accepts that loss explicitly, as a forced `EmergencyReparentShard` does. `DeleteTablets` refuses to delete the record of the shard's PRIMARY tablet unless it is given `--allow-primary`: on a live primary, that deletion does not stop it, and it keeps acknowledging writes until VTOrc moves the group primary to another voter (MoveGroupPrimaryToVoter), about one recovery cycle; should it crash before that, its removal loses what it acknowledged meanwhile, which `--allow-primary` accepts; VTOrc never removes a voter whose record exists, and keeps a deleted voter whose MySQL is still active in the group (`GroupVoterRecordDeleted`).

#### The bootstrap candidate

Which voter bootstraps the group matters as much as when. Every acknowledged transaction was committed by the primary that acknowledged it, so it is in a voter's **executed** set, its binlog; a transaction a voter only **received** sits in the relay log of its `group_replication_applier` channel, which a restart of mysqld discards (`relay_log_recovery=ON`). MySQL 8.4.11 treats that relay log as follows (lab, `doc/failover-audit/GroupReplication.md`, "Bootstrap candidate"):

- A member that **bootstraps** applies it before it becomes ONLINE.
- A member that **joins** a group applies it first, when its `START` begins; if the group lacks those transactions, MySQL then refuses the join for good ("This member has more executed transactions than those present in the group"). The group does not diverge, but that member can never join it.
- With Group Replication stopped, `START REPLICA SQL_THREAD FOR CHANNEL 'group_replication_applier'` applies it into the binlog, and survives a restart.

So the new group must hold every transaction that any voter executed **or received**, and its first member must have them in its binlog before its `START`. Requiring a voter that **executed** every transaction is not enough to choose one: a transaction that the group decided while its primary crashed before committing it can sit in a relay log only, never acknowledged, executed by no voter; such a rule would never bootstrap the group (the TLA+ model's `cand_strict` configuration gets stuck). The rule:

1. **VTOrc** computes the union of every voter's executed and received sets, the *required set*, and considers the voters whose executed and received set contains it, as before. Among them it prefers the target of a live bootstrap intent, then a voter that already **executed** the whole required set (typically the old primary), then a voter without a `START` in progress, then the PRIMARY tablet, then the lowest alias.
2. The bootstrap RPC carries the required set (`StartGroupReplicationRequest.required_gtid_set`). Under the action lock, right before MySQL's `START`, the tablet applies its relay log if its executed set lacks part of it and the relay log holds the rest, and refuses with `FAILED_PRECONDITION` unless its executed set then contains the required set. The apply waits at most `groupReplicationRelayLogApplyTimeout` (30s), and ends `groupReplicationRefusalReserve` (5s) before the RPC's deadline, so that a refusal reaches VTOrc before it gives up: VTOrc withdraws the bootstrap intent only on a definitive refusal it receives (see "Bootstrap intent"). VTOrc reads every voter again and chooses again on its next pass.

**Safe:** when MySQL starts the bootstrap, its binlog holds every transaction any voter executed, so every acknowledged one, and no restart can take them away; every other voter can join, since the group holds everything it executed or received. A restart that discarded the candidate's relay log after VTOrc's read makes the tablet refuse, rather than create a group without those transactions (the model's finding 1). **Live:** some voter's executed and received set always contains the required set once every voter is reachable, unless the voters diverged (VTOrc then refuses, as before); that voter can apply its own relay log, so the check passes unless mysqld restarted, after which the next pass computes a smaller required set from what is left. A restart that makes the candidate refuse adds no wait: the refusal is definitive, and VTOrc withdraws the intent written for the candidate at once (see "Bootstrap intent"), so that its next pass bootstraps the voter that holds what the candidate lost. When the RPC fails without a definitive refusal instead, for example when it reaches the tablet while mysqld is still down, VTOrc keeps the intent; once the candidate answers again, in no group and without a `START`, VTOrc sends it the intent's bootstrap again, which it refuses definitively, and bootstraps the voter that holds what the candidate lost in the same pass (see "Bootstrap intent", a stale intent). The intent fences the other voters for its two minutes only while the candidate does not answer, or runs a `START`.

## Architecture

### Durability policy and replication mode

`policy.Durabler` stays unchanged, so out-of-tree policies keep compiling. A policy can additionally implement:

```go
type ReplicationModer interface { ReplicationMode() ReplicationMode }       // Async | GroupReplication
type GroupReplicationDurabler interface {
    Durabler; ReplicationModer
    IsGroupMember(*topodatapb.Tablet) bool      // may be a voting member (vs always an async replica)
    MemberWeight(*topodatapb.Tablet) int        // group_replication_member_weight
}
```

One policy is registered, `group_replication_cross_cell`. PRIMARY and REPLICA tablets are eligible voters, with **one voter per cell** and at most 9; other types replicate asynchronously from the group's primary, and `SemiSyncAckers()` is 0. No cell can hold a majority of the voting members: every acknowledged transaction has been accepted by a member in another cell, which is the GR equivalent of `cross_cell`; see "What an acknowledged commit guarantees" for what accepted means once the group loses its majority. The other PRIMARY/REPLICA tablets of a cell replicate asynchronously. VTOrc reports a cell majority as a violation. The one-voter-per-cell rule is not a setting of the policy: every component applies it.

A shard needs eligible tablets (PRIMARY or REPLICA) in at least three cells (`policy.MinGroupReplicationCells`): with one voter per cell, a group of two voters keeps no majority when one of them fails. Every component that starts a group checks it, before it changes anything:

- the initial promotion of `PlannedReparentShard` and `InitShardPrimary` refuse with `FAILED_PRECONDITION`, and name the cells they found (`reparentutil.CheckGroupReplicationCells`);
- the preflight of `MigrateReplicationMode` refuses (see "Migration");
- VTOrc writes no initial voter list, and so bootstraps no group, while its selection has fewer than three voters: it reports `GroupVotersBelowTarget` instead, which has no recovery, until the shard has eligible tablets in a third cell.

An earlier `group_replication` policy without the per-cell limit was removed before any release: with more than one voter in a cell, a cell could hold the majority of the voters, and the loss of that cell lost acknowledged transactions.

Which eligible tablets actually vote is recorded per shard; see "Voters" below.

### Principle: the observed MySQL state decides the behaviour, the policy decides the goal

Every tablet reports whether its MySQL is an active member of a group (`ONLINE`/`RECOVERING`). Tablet RPCs dispatch on that observed state, not on the policy:

- On an active member, replication RPCs have GR meaning. `SetReplicationSource` never touches the default channel; `PromoteReplica` calls `group_replication_set_as_primary`.
- On a non-member, they keep their asynchronous meaning, even if the keyspace policy says GR. Those are the async replicas of the group, or tablets that are not converted yet.

The policy only defines the target: who should be a member, with which weight, and whether semi-sync is still required. This makes the half-migrated states of an online conversion well defined.

Corollary: **an active group with at least two ONLINE members supersedes semi-sync.** On such a primary neither the tablet nor VTOrc demands semi-sync, whatever the policy says. This rule is what lets a shard run its group while its policy is still `semi_sync`, during its own conversion.

**The policy is a shard's.** The observed state cannot decide everything: whether a primary that lost the majority of its voters stops serving, whether a voter rejoins its group, whether VTOrc bootstraps a group or replaces a voter, and whether ERS and PRS take the Group Replication path, are decisions about the target, and the target is the policy's. A keyspace is converted one shard at a time, so while it is half migrated its shards have different targets. The policy that applies to a shard is therefore resolved per shard, by a single resolver used by every component (`topo.ShardDurabilityPolicy`): **the shard's own policy (`Shard.durability_policy`) if its shard record sets one, else its keyspace's.** Only `MigrateReplicationMode` sets a shard's own policy, under the shard lock, at a fixed step of the shard's conversion, and removes it once the keyspace has the same policy (see "Migration"). Outside a migration no shard has a policy of its own, and the keyspace's applies, as before.

- **vtctld** (`reparentutil`, `grpcvtctldserver`, `wrangler`) resolves it from the shard record it read under the shard lock (`topo.Server.GetShardInfoDurability`): PRS, ERS, `InitShardPrimary`, and the semi-sync setting of the replicas it repoints.
- **VTOrc** keeps the shard's own policy in its copy of the shard record (`vitess_shard.durability_policy`) and resolves it in the detection analysis, for every analysis of the shard, Group Replication and asynchronous alike. Its recoveries resolve it again after they refreshed the keyspace and shard records under the shard lock (`inst.GetShardDurabilityPolicy`), or from the shard record they read from the topology under the lock (`inst.GetShardRecordDurabilityPolicy`): bootstrap, voter replacement, primary move, stale primary, and the semi-sync fixes.
- **vttablet** reads the shard record and the keyspace record together (`shardDurability`), so that it never combines a shard record and a keyspace record of different moments of a migration. The sync loop caches the result for 10s, but drops the cache as soon as a shard record it reads (every 5s while its MySQL is in a group, and before every promotion) sets another own policy than the one it resolved with. Before it stops serving for a lost voter majority, it resolves the policy again from the topology, as before. Every RPC that changes the group (a join, a bootstrap, the primary's leave) resolves it from the topology.

### Voters

A group should be small: every commit waits for a majority of the voting members, and flow control follows the slowest of them. One member per cell already makes every commit wait for a member of another cell, so more members per cell add cost without adding durability. A shard therefore has a fixed set of **voters**, the tablets that are voting members of its group. Every other PRIMARY, REPLICA or RDONLY tablet replicates asynchronously from the primary, as all Vitess replicas do today.

- **Where.** The voters are stored in the shard record, `Shard.group_replication_voters` (a list of tablet aliases), so vttablet, VTOrc, PRS, ERS and the migration all agree on them. Only listed tablets join the group, and only listed tablets rejoin it on their own; a tablet that is not listed stays, or becomes, an asynchronous replica. Under a group replication policy an **empty list means "not selected yet"**: the components then fall back to the policy (every eligible tablet counts as a voter) until one of the writers below fills it in.
- **Who writes it**, always under the shard lock:
  - `MigrateReplicationMode`, before it bootstraps the group, and when converting back, after the last member left the group, it clears the list.
  - `PlannedReparentShard`, on the initial promotion of a shard that never had a primary, before `InitPrimary` bootstraps the group.
  - VTOrc, with the actions below.
- **Selection of the first list** (`policy.SelectVoters(durability, current, groupPrimary, candidates)`), which the migration, the initial promotion of PRS and VTOrc use when no voter is listed. It changes the current voters as little as possible:
  1. The group's primary always keeps its seat; removing it would force a failover.
  2. A current voter is kept while it is eligible (`IsGroupMember`) and has not failed, within the limit of its cell.
  3. Active members come next, so that a tablet already in the group is preferred to one that would have to join.
  4. Free seats go to eligible, non-failed tablets, by promotion rule, then lowest alias.

  Every cell is limited to one voter, and the group to 9. The result is deterministic, so every writer computes the same list from the same inputs.
- **VTOrc's changes** (`inst.PlanGroupVoters`). VTOrc's analysis proposes a change on its stored state (`GroupVotersOutOfDate`), and the recovery decides it on **one bounded fresh read** under the shard lock: the shard record, and the `FullStatus` of every tablet of the shard, read concurrently within 2s (`groupVoterStatusesTimeout`). It then writes the new list with a **compare-and-swap** on the voter list and the incarnation it read, with nothing in between: no second read and no RPC. A VTOrc whose lock expired, or a component that wrote the list or recorded an incarnation since, makes the write fail with `FAILED_PRECONDITION`, and the next pass decides again. The changes need some of these preconditions, on that read:
  - **P1, a settled legitimate primary** `p`: a voter whose MySQL is the ONLINE primary, with quorum, of a view of the recorded incarnation (which must be set), whose election has ended (`primary_election_in_progress`, `GroupReplicationStatus` field 14, false), and whose view holds a majority of the voters ONLINE.
  - **P2, the voter `v` is active in no view**: its tablet does not answer (for a voter whose tablet record was deleted, at the address VTOrc last knew, read in the same read), and no reachable member of the recorded incarnation reports its server_uuid ONLINE or RECOVERING. When VTOrc does not know its server_uuid, every member that a reachable member reports active must be the MySQL of a tablet that answers.
  - **P3, a valid spare `x`**: not a voter; a REPLICA that the policy allows as a voter; it answers; its MySQL is not an active member, runs no `START GROUP_REPLICATION` and is in no group (also not in the ERROR state of one); it executed nothing that `p` lacks; and no other voter of the new list is in its cell.

  The actions, of which a pass makes at most one:
  1. **Initial list.** No voter is listed, no incarnation is recorded, every tablet that may be a voter answers, and no member is active: `SelectVoters`, one voter per cell, written only with at least three voters (`GroupVotersBelowTarget` otherwise). A shard whose group runs without a voter list gets the alert instead.
  2. **SwapVoter(v, x).** `v` has been unreachable for `--group-replication-voter-replacement-grace-period` (VTOrc flag, default 1m), or its tablet record was deleted. Needs P1 with `p ≠ v`, P2 and P3 with `x` in `v`'s cell. Writes `V \ {v} ∪ {x}`; then `x` joins the group. A voter that is only briefly unreachable, for example while it restarts, or whose MySQL is still active in the group while its vttablet is down, keeps its seat.
  3. **GrowVoter(x).** A cell with an eligible tablet has no voter, for example a new cell, or the cell of a voter that was removed. Needs P1, P3 with `x` in that cell, and a majority of the grown list among the voters ONLINE in `p`'s view, so that `p` keeps serving under the new list before `x` joins. Writes `V ∪ {x}`, up to 9 voters; then `x` joins.
  4. **MoveGroupPrimaryToVoter** (`GroupPrimaryNotVoter`). The primary of the shard's legitimate group is not a voter, so it does not serve (see "Serving invariant"), or it is a voter whose tablet record was deleted: VTOrc moves the group primary (`PromoteReplica`, `group_replication_set_as_primary`) to an ONLINE voter of its view, chosen as for the move out of an unreachable cell. The list does not change. A primary whose record was deleted is found as the primary that the reachable members of its view report, by its server_uuid or, when VTOrc does not know it, as a primary that is the MySQL of no tablet with a record.
  5. **RemoveVoter(v).** `v`'s tablet record was deleted (`DeleteTablets`; a cell's decommission also runs `RemoveKeyspaceCell`) and its cell has no valid spare. Needs P1 with `p ≠ v`, P2, and `v` in no view of `p` (when VTOrc does not know `v`'s server_uuid, every member of `p`'s view must be the MySQL of a tablet that answers). Writes `V \ {v}`. Deleting the tablet record is the operator's decision to shrink the group: VTOrc never removes a voter on its own.
  6. **RemoveVoterNoGroup(v).** `v`'s tablet record was deleted while no group runs: no reachable tablet is an active member of any incarnation or runs a `START GROUP_REPLICATION`, no bootstrap intent is live (what VTOrc last saw on a deleted voter that it no longer reaches does not count: VTOrc keeps discovering a deleted voter while it is listed, and its stale state would otherwise make the shard look like one with a group, whose missing `PRIMARY` tablet an emergency reparent would try to replace), and `v` is down: its vttablet does not answer at the address VTOrc kept, and VTOrc's discovery has not reached it for the grace period. Every other voter must answer, in no group and without a `START`. A deleted voter that still runs may hold transactions that the others lack, but it cannot be part of the bootstrap either, which needs every voter's tablet record (`only N of the M voters of the shard have a tablet`): VTOrc reports `GroupVoterRecordDeleted`, and the operator stops its vttablet and MySQL, or restarts its vttablet, which records the tablet again. A group that lost the majority of its voters otherwise stays down for as long as a voter is gone for good, since VTOrc bootstraps only when every voter answers (`GroupNotBootstrapped`). Writes `V \ {v}`, keeping at least one voter; `GroupNotBootstrapped` then bootstraps the group from the remaining voters, with its usual candidate rules, over their transactions. The transactions that only `v` held are lost: see "What an acknowledged commit guarantees".

  RemoveVoter and RemoveVoterNoGroup are the only changes that shrink the list, and only they may leave fewer than three voters. VTOrc changes nothing else: it neither re-seats a group primary that is not a voter, nor makes a member that is not a voter leave the group (its tablet does, see "Joining"), nor drops a voter that changed to an ineligible type. When it changes nothing, it reports, without a recovery: `GroupVoterRecordDeleted`, a voter whose tablet record was deleted while its MySQL is still active in the group, or still in `p`'s view and without a spare; `GroupVoterUnreplaceable`, a voter that failed while its cell has no valid spare; and `GroupVotersBelowTarget`, fewer voters than cells with an eligible tablet, or fewer than three.

  Why these preconditions: a list written while a view that lacks a majority of the current voters could hold a majority of the new list would let that view serve again on fewer hosts than a majority of the voters (see "Group shrink fails closed"); P1 rules it out, since every change keeps or grows the voters that `p`'s view holds ONLINE, and a spare joins only through distributed recovery, which gives it the group's history. A voter that the group still sees active (P2), or a spare that already executed what the group lacks or is in another group (P3), could hold or bring transactions that the new list does not cover. And a change decided on statuses read earlier than the write could miss a voter that came back, was elected, acknowledged a transaction and failed again meanwhile (the TLA+ model's `voters_split`): the single fresh read right before the compare-and-swap, and the settled check, close that window. What remains is the time between that read and the end of the compare-and-swap, at most about 2s plus the write's round trip to the global topology, unless VTOrc itself stalls.
- **Promotion.** Only a voter can become the primary. Swapping a non-voter in for a voter as part of a planned reparent is future work.

### The legitimate group

Group Replication decides which member is the primary, and Vitess follows it. But Vitess must only follow the shard's **legitimate** group, and must not create the conditions for a new one. The chaos tests found that a member that had just left its group, and was made to join again while the other members were leaving too, ended up alone in a new group: MySQL installed a view of a new *incarnation* (the part of the view id before the `:`) that contained only this member, which was ONLINE, PRIMARY and had quorum in its view of one. The tablet promoted itself, and every transaction that only the other members held was lost (`doc/failover-audit/GroupReplication.md`, NEW-1).

- **Incarnation.** `Shard.group_replication_incarnation` records the incarnation of the shard's group. MySQL keeps it for as long as the group exists, and every bootstrap creates a new one. Whoever bootstraps a group records it under the shard lock, right after the bootstrap: `MigrateReplicationMode`, the initial promotion of `PlannedReparentShard` (and `InitShardPrimary`), and VTOrc's `BootstrapGroupReplication`. Every write is a compare-and-swap against the incarnation the writer read before it changed the group, and fails with `FAILED_PRECONDITION` if another component recorded one meanwhile. The reverse migration clears it with the voters. An empty value means unknown (a group bootstrapped before incarnations were recorded); only the voter rule below applies then.
- **Bootstrap intent.** VTOrc records `Shard.group_replication_bootstrap_intent` (the target tablet, the time, the incarnation the shard record listed, a token) under the shard lock before it bootstraps, and the incarnation write clears it. If the bootstrap's reply is lost (the RPC times out, the tablet is cut off again while MySQL's `START` runs, VTOrc stops), VTOrc *adopts* the group: right away when the RPC fails, or on a later pass through the analysis `GroupBootstrapNotRecorded`, it re-reads the shard record and the target's status under the shard lock, and records the group's incarnation when all of these hold: the group's ONLINE primary, with quorum, is the intent's target; its incarnation differs from the one the intent was recorded for; and it was created after the intent. The last holds by construction, since VTOrc writes the intent only after a fresh read of every voter under the shard lock found none of them in a group; the time MySQL encodes in the incarnation (the view id's fixed part, in units of 100ns since the epoch) must not contradict it by more than 30s. A member that a failed join left alone in a group of its own, a stray incarnation, is never adopted unless it is the intent's target, the voter VTOrc found to hold every other voter's transactions, for which such a group is what the bootstrap creates. An intent younger than two minutes also **fences** a bootstrap on another tablet (`FAILED_PRECONDITION`), by this or another VTOrc: a bootstrap whose reply was lost may still be running with its member not active yet, and VTOrc's check that no voter is active cannot see it. A bootstrap of the same target is not fenced: the tablet stops a `START` still in progress first, and a member that is already active refuses the bootstrap, which leads to the adoption. Among voters with equal GTID sets, VTOrc therefore chooses the target of a recent intent again, before the shard primary and the lowest alias: the old primary's tablet demotes itself during the outage, which otherwise changed the choice and left the next bootstrap fenced. The fence outlasts the minute for which the tablet trusts a group it bootstrapped. A bootstrap that its target refuses **definitively** lifts the fence at once: when MySQL lacks a transaction that the request requires (see "The bootstrap candidate"), and a fresh read of its status under the action lock finds it in no group and no `START GROUP_REPLICATION` running (`performance_schema.processlist`), the tablet reports the refusal as definitive (`StartGroupReplicationResponse.definitive_refusal`, only when the request sets `report_definitive_refusal`, which VTOrc does), and VTOrc *withdraws* the intent under the shard lock, which it re-checks first: a compare-and-swap that removes the intent only while the shard record holds its token, for the incarnation it was recorded for, and leaves a newer intent or an incarnation recorded since as they are. Its next pass chooses again. The refusal proves that the RPC did not start MySQL's bootstrap and never will: every `START` of the tablet runs under its action lock, which the RPC holds until it returns; MySQL starts none on its own; and VTOrc sends an intent's bootstrap again only after its earlier RPC failed (see a stale intent, below). No refusal is definitive while a `START` runs: one that an earlier RPC issued before its client gave up can still form a group of one, which a withdrawn intent could no longer adopt, next to a bootstrap of another voter. Any other failure (a timeout, a lost reply, a transport error, a refusal of a superseded intent or of an active member, a refusal while a `START` runs) keeps the intent, for adoption or expiry. An RPC of an older intent that still waits for the tablet's lock is refused by the token check, since the shard record no longer holds its token (unless the tablet's topology does not answer, as before). A tablet that does not know `report_definitive_refusal` refuses with an error, and VTOrc keeps the intent, as before. An intent that does not apply to the incarnation the shard record lists (a component that does not know intents recorded another incarnation) is ignored. Readers that do not know the field ignore it.

  **A stale intent.** An RPC that fails without a definitive refusal keeps its intent, and its target may then lose transactions that another voter holds: its mysqld restarts and discards its relay log. VTOrc no longer chose that voter, so nothing refused the intent's bootstrap, and the intent fenced the bootstrap of the voter that holds those transactions until it expired. When a live intent names a voter other than the candidate, VTOrc now first sends that intent's bootstrap to it again, at most once per pass, if all of these hold on that pass: the voter's tablet answered `FullStatus`; its MySQL is not an active member (a group it formed is adopted instead, through `GroupBootstrapNotRecorded`); no `START GROUP_REPLICATION` runs on it (that `START` could still form a group of one, and the intent keeps fencing the other voters, also once VTOrc's 10s grace for a `START` has passed); it is still a voter with a tablet record; and the intent has a token. The request carries the intent's token and the incarnation it was recorded for, the required set computed on this pass, and `report_definitive_refusal`. VTOrc does not write the intent: its time, and the fence, are never extended. The tablet needs no change, and decides as for any bootstrap: under its action lock, it checks the token and the incarnation, applies its relay log if that covers what MySQL lacks, and refuses definitively when MySQL still lacks a required transaction and no `START` runs. A voter that is no longer the candidate refuses definitively, unless something changed meanwhile. VTOrc then withdraws the intent with the compare-and-swap, reads the shard record and every voter again, and bootstraps the candidate in the same pass, under the same shard lock, which the intent's write checks first: the fresh read takes a few milliseconds and saves a pass of VTOrc. A target that bootstraps after all executed every required transaction, which its tablet checks right before MySQL's `START`; its group is recorded as the intent's, with the compare-and-swap, as for the intent's first RPC. Any other failure keeps the intent, for adoption or expiry. The definitive refusal still proves that no bootstrap starts from the intent although its token was sent twice: the first RPC failed before VTOrc sent the second, and if its handler still waits for the tablet's action lock, the token check refuses it once the intent is withdrawn, and before that its own required set does: computed on an earlier pass, it holds what the target lacks now, since the union of the voters' executed and received sets only shrinks while no group runs. Two VTOrcs, or one that resumes after its lease expired, act under the shard lock, which every intent write re-checks, and through the same compare-and-swaps; a re-probe of an intent that another VTOrc wrote is the same RPC as that VTOrc's.
  - **The RPC carries its intent.** The fence assumes that a bootstrap acts only while its intent is the shard's, but the RPC can wait for the tablet's action lock while its VTOrc loses the shard lock and another VTOrc replaces the intent, bootstraps the group, records it, and, the group gone again, bootstraps another voter: the stale RPC then bootstrapped a second group from the same recorded incarnation (the TLA+ model's finding 2). VTOrc therefore sends the intent's token and the incarnation the intent was recorded for (`StartGroupReplicationRequest.bootstrap_intent_token`, `expected_incarnation`), and the tablet reads the shard record and refuses with `FAILED_PRECONDITION` if it no longer holds that intent, or lists another incarnation: when the RPC gets the action lock, before it changes anything (a PRIMARY tablet keeps serving, its rejoins stay as they were); before each `STOP` of a `START GROUP_REPLICATION` in progress, which may be the bootstrap of the newer intent, whose group VTOrc is to adopt; and right before MySQL's `START`. Each read waits at most `groupReplicationTopoReadTimeout` (1s), like the bootstrap's other topology reads, so the action lock is never held across an unbounded read. When the topology does not answer in time, the tablet bootstraps without the check, as before it: the check protects the availability of the shard's group, which a bootstrap that the topology keeps from running would cost too (the model's `stale_rpc_timeout`). A request without a token is not checked; VTOrc is the only component that sends bootstrap intents. A refused RPC leaves VTOrc's adoption untouched: the adoption's compare-and-swap is against the stale intent's token, and fails; the shard record's current intent is adopted by its own VTOrc or by `GroupBootstrapNotRecorded`.
  - **A late reply keeps a newer intent.** Recording an incarnation that the shard record lists already (a VTOrc that adopted the group first, then the bootstrap's own reply) clears only an intent recorded for an earlier incarnation. An intent recorded for this incarnation was written after it, by a VTOrc that found the group gone again, for a bootstrap that may still run; clearing it removed its fence, and left its group impossible to adopt (found by the model once the token check was in place).
- **Legitimate primary** (`policy.LegitimateGroup`). A member is the primary that Vitess follows when it is the ONLINE primary of a group with quorum in its own view, its view belongs to the recorded incarnation (if one is recorded), and a **majority of the listed voters are ONLINE in its view**. Voters are found in a view by the `server_uuid` of their MySQL (from `FullStatus`) or by the MySQL address of their tablet record (`MEMBER_HOST`/`MEMBER_PORT`; MySQL reports its own hostname, which need not match the tablet record). With no voter listed, MySQL's own view quorum applies, as before.
- **Unreachable cells.** The tablet records only give the voters' MySQL addresses. They are read cell by cell, each cell with its own 2s deadline (`topo.GetTabletMapForShardWithCellTimeout`): the topology server of a cut-off cell does not answer until the caller gives up, and a single deadline for all cells made the reads of the other cells fail too. A voter without a tablet record is still found by its known `server_uuid`. The reconcile loop reuses the tablet records it read within 30s as long as they, with the known `server_uuid`s, identify every voter, so the promotion of a member elected while the old primary's cell is partitioned does not wait for that cell (S9i chaos scenario: 139s without a primary before, 9.0s after). VTOrc's `PromoteGroupPrimary` and its join check read the tablets the same way and accept a partial result.
- **Where it applies.** The tablet's reconcile loop only promotes a legitimate primary. VTOrc's `GroupPrimaryNotInTopo`, its `PromoteGroupPrimary` recovery, its notion of the group's primary for its voter changes (`GroupVotersOutOfDate`, `GroupPrimaryNotVoter`), ERS's search for the group's quorum, and the PRS preflight all use the same rule.
- **Foreign incarnation.** A member that is active in a group of another incarnation than the recorded one does not hold the shard's acknowledged transactions. Before Vitess disabled the member action `mysql_disable_super_read_only_if_primary`, MySQL made the primary of such a group writable: a voter's join that did not find its group has been seen to complete as the only member of a new incarnation, ONLINE PRIMARY and writable on a REPLICA tablet, for 5.7s before the tablet had left it (1s for the sync loop to notice, 4.7s for `STOP GROUP_REPLICATION`). MySQL now keeps it read-only, since the joiner's own configuration, which such a group uses, has the action disabled; the tablet's fence check (see "Fence check") would also set `super_read_only` within about 150ms, without waiting for the sync loop or the action lock. The tablet then makes MySQL leave that group, fencing it first if the sync loop got there first (`STOP GROUP_REPLICATION`; MySQL stays `super_read_only`), and demotes itself if it was PRIMARY. It then rejoins the legitimate group like any voter that is out of it (see "Joining"): its own rejoins are not suspended, since the group may need this voter to get a majority, and so a primary tablet, back. A tablet that bootstrapped a group itself trusts its incarnation for a minute (`groupReplicationBootstrapGrace`), until the component that asked for the bootstrap has recorded it; a mismatch with the cached shard record is always confirmed with a fresh read.
  The new group of which the tablet's MySQL is the primary while a live bootstrap intent names the tablet, under the conditions in which VTOrc adopts it (see "Bootstrap intent"), is not foreign either: the tablet neither fences nor leaves it, since leaving it left VTOrc nothing to adopt, and it does not serve it before VTOrc records or adopts its incarnation (the serving invariant). It is the group of a bootstrap whose reply was lost before the tablet noted it, or a group of its own that a join of the intent's target ended in; VTOrc adopts either, and it is the group the tablet would trust had the bootstrap's reply arrived. A tablet that fenced it before it read the intent keeps it fenced, without leaving it; its promotion after the adoption lifts the fence.
- **Joining.** A tablet (at startup and in its reconcile loop) and VTOrc (`GroupMemberNotOnline`) only start a join while another tablet of the shard reports an active member of the legitimate group with quorum in its view. The tablet asks its peers' `FullStatus` with a 2s timeout, the shard primary first; VTOrc asks every tablet of the shard, returns as soon as the answers settle the question, and waits at most 2s for the others, so that the join starts right after a current check (a check that waited 9s for an isolated tablet started a join into a group that had lost its majority meanwhile). VTOrc's recovery does not need a shard primary tablet: a group that was just bootstrapped, or lost the majority of its voters, only gets one once enough voters have joined it. After a bootstrap, VTOrc makes the other voters join the new group right away. A `START GROUP_REPLICATION` with no group to join cannot join anything: it blocks until MySQL's join timeout, and MySQL refuses a bootstrap on the same member meanwhile (`errno 3724`), which starved VTOrc's bootstrap (NEW-2 of the audit). Such joins are also where members formed groups of their own. MySQL keeps running a `START` whose client gave up, so the reconcile loop waits up to a minute for the joins it starts, and any join or bootstrap first stops a `START` still in progress.
  - **A `START` in progress.** Such a `START` reports the member OFFLINE for its whole duration, up to 61–67s when it finds no group, not RECOVERING; it can still end with the member alone in a group of its own (sro-eval case A). VTOrc therefore took the member for one that it may bootstrap another voter next to. `GroupReplicationStatus.start_in_progress` reports it, from `performance_schema.processlist`, which lists the `START` for as long as it runs, also after its client connection was killed, and from the tablet's own joins and bootstraps in progress (`FullStatus`). VTOrc does not join such a member again (`GroupMemberNotOnline`), counts it as active for `GroupNotBootstrapped`, and `BootstrapGroupReplication` refuses to bootstrap while any tablet reports one, for at most `groupStartInProgressGrace` (10s) from the moment VTOrc first observed it; then it bootstraps anyway, preferring among equal voters one without a `START`. `ClusterHasNoPrimary` and `PrimaryTabletDeleted` keep ignoring a shard without an active member. The tablet's sync loop does not start a join while MySQL runs a `START`.
    The bound is the liveness trade-off. VTOrc cannot shorten a `START`: MySQL refuses to stop it (errno 3663) until it ends. While no member is active, which is when the group needs a bootstrap, a `START` cannot join anything; a group of its own that it forms stays read-only (the member action is disabled), its tablet leaves it as a foreign group, or VTOrc adopts it if its member is the target of a bootstrap intent. In the G12 chaos scenario, a gate without a bound waited for the joiner's `START` to end 6–22s after the heal (it formed a read-only group of one, which its tablet then left), and outages grew from 30.7–40.9s to 36.8–54.8s per cycle; see "Audit: only Vitess makes MySQL writable".
  - A joining member contacts first the peers that were just seen active in the legitimate group (`group_replication_group_seeds` order), also for a join that the `StartGroupReplication` RPC requests (VTOrc's joins after a bootstrap, `GroupMemberNotOnline`): the tablet reads its peers' status first (`refreshActiveGroupSeeds`, without the action lock). Right after a bootstrap that is the bootstrapped member. The other peers come after it, in their sorted order: in the G12 chaos run, the first sorted seed was a restarted voter whose own `START` was stuck, and each such join waited out MySQL's 30s timeout for the group communication engine before it tried the next seed.
  - **No join before the incarnation is recorded.** While the shard record lists no incarnation, every group counts as the shard's group, also a group of one that a join formed when the member it joined left (the TLA+ model's `init_orc_lost`: a voter joined VTOrc's unrecorded bootstrap, the bootstrapped member left, the joiner ended alone in a new incarnation, a third voter joined it, its primary served and acknowledged a write, and VTOrc then recorded the first incarnation). A tablet therefore starts no join on its own (at startup, in its reconcile loop) while the shard record lists no incarnation, VTOrc's `GroupMemberNotOnline` does not match then, and its voter replacement starts no join on a new voter. The component that bootstraps records the incarnation and then joins the voters (VTOrc, the migration), or the voters join on their own once it is recorded (the initial promotion). A group that runs unrecorded, for example after an initial promotion whose record failed, is recorded by VTOrc's `GroupBootstrapNotRecorded` when it is the only group the shard can have (below).
  - **A joining member takes no asynchronous replication.** A tablet whose MySQL runs a `START GROUP_REPLICATION` refuses `SetReplicationSource` (FAILED_PRECONDITION): the default channel configured during a join ran next to the membership that the `START` completed, and the replication lag poller then read that channel (G13 chaos run).
- **Serving invariant.** Under a group replication policy that lists voters, a tablet starts or resumes serving as PRIMARY only if, at the moment of the decision, its MySQL is the ONLINE primary, with quorum, of a view of the shard's *recorded* incarnation that holds a majority of the listed voters ONLINE, and the tablet itself is a listed voter (`groupReplicationServingReason`). A member that is not a voter counts in the certification majority of its view, which then need not hold a majority of the voters, so what it acknowledged need not be on a majority of them; a join completes after the voter list dropped its tablet, since MySQL finishes a `START` whose client gave up, and the group can elect such a member. Its tablet becomes a PRIMARY that does not serve (`groupReplicationNotVoter`), MySQL stays read-only, and VTOrc moves the group primary to a voter (`GroupPrimaryNotVoter`), whose tablet serves then. As defense in depth, a primary that a voter list written later drops is fenced as soon as the tablet reads that list from its shard watch, as for a lost voter majority, rather than on its next decision (the model does not need it once VTOrc decides every change on one fresh read right before its compare-and-swap). A member that is not a voter and not the group primary leaves its group on the tablet's own (the sync loop, after it read the voter list again under the action lock), when the group keeps a majority of its members without it; VTOrc never makes a member leave. A tablet whose own tablet record was deleted never becomes PRIMARY: becoming PRIMARY writes the record first, which then fails at once (`FAILED_PRECONDITION`). Nor does a PRIMARY tablet serve again once it stopped: it reads its record first (`serveAgain`, `UndoDemotePrimary`). A primary that still serves when its record is deleted (`DeleteTablets --allow-primary`) keeps serving until VTOrc moves the group primary away from it (`GroupPrimaryNotVoter`); a publish that finds the record gone shuts the tablet down, as before. Not the incarnation of a group the tablet bootstrapped itself: until VTOrc records or adopts it, the tablet may be PRIMARY but does not serve. "At the moment of the decision" means under the tablet's action lock, which the bootstrap and every other RPC that changes MySQL's group hold, and on a status of MySQL read after acquiring it; the shard record is read before taking the lock, so that the lock is never held across a topology read. Every not-serving reason that is set also counts as a new decision with a generation, and a decision to serve again only clears a reason set before the status it read. Every path that makes a PRIMARY serve decides this way: the sync loop serving again (`serveAgain`), every promotion through `changeTypeLocked` (the loop's own, `PromoteReplica` for PRS, ERS and VTOrc, `InitPrimary`, `ReplicaWasPromoted`, `ChangeType`), `UndoDemotePrimary`, `DemotePrimary`'s revert, and a primary that leaves its group. Stopping to serve needs no lock: the loop stops on the status it read at the start of its run, even if that run then waited on an unresponsive topology. In the S7d chaos scenario such a run read MySQL's status while MySQL was the primary of two voters, waited for the topology of its cut-off cell, and after the heal made the tablet serve again 16ms after VTOrc's bootstrap had stopped it; the bootstrap then made MySQL the writable primary of a group of one, which acknowledged 132 writes in 1.3s (see "Serving invariant" in the audit). The invariant is about the decision: a group whose view shrinks under a serving primary, because a voter leaves cleanly, is the fence check's (see "Group shrink fails closed").
- **Only Vitess makes MySQL writable.** With the member action `mysql_disable_super_read_only_if_primary` disabled (see "Group configuration"), every primary that Group Replication elects stays `super_read_only`: a bootstrapped primary, the primary that `group_replication_set_as_primary` or a failover elected, and the primary of a stray group of one (sro-eval case B, MySQL 8.4.11; with the action enabled, the same stray group took 133 commits). MySQL is made writable only by a decision of its tablet that it may serve as PRIMARY, under the action lock, on MySQL's status read under it, with the serving invariant holding (under a group replication policy that lists voters), and after a fence snapshot: a fence decided since stands. The decisions are `changeTypeLocked` (the sync loop's promotion, `PromoteReplica` for PRS, ERS and VTOrc, `InitPrimary`, `ReplicaWasPromoted`, `ChangeType`), `serveAgain`, `UndoDemotePrimary`, the end of a planned pause (`waitForWritablePrimary`), the end of a join or bootstrap of a PRIMARY tablet (`finishGroupJoinLocked`), `SetReadWrite`, and a primary that leaves its group. A promotion that the serving invariant refuses leaves MySQL read-only, and redoes the prepared transactions later, with the decision that lets it serve.
  - **The end of the election.** Under `BEFORE_ON_PRIMARY_FAILOVER` a new primary reports itself PRIMARY before it has applied its backlog, and when the election ends Group Replication sets `super_read_only` again, undoing an earlier clear (sro-eval b2: a clear made while the new primary's backlog was blocked held for 6s, until the election ended and set `super_read_only` again; the write held meanwhile failed with errno 1290). The election runs as long as `performance_schema.threads` lists `THD_primary_election_primary_process`, which `GroupReplicationStatus.primary_election_in_progress` reports. Every decision first waits for it to end (at most `groupReplicationElectionWaitTimeout`, 10s; `PromoteReplica` and `InitPrimary` for their RPC's deadline), and a primary whose election still runs does not serve (reason `MySQL's replication group is still electing it its primary`); making MySQL writable is refused meanwhile (`UNAVAILABLE`). The sync loop does not take a not-serving decision on an election it read at the start of its run: the promotion of the same run may have waited for its end.
  - **A serving primary that is read-only.** Should the end of an election set `super_read_only` after the decision (MySQL may report itself PRIMARY a moment before the election thread runs), the fence check, which reads `super_read_only` on a PRIMARY every 150ms, wakes the sync loop, and `serveAgain` makes MySQL writable again under the same decision. A primary that `DemotePrimary` demoted is left alone (`groupReplicationDemoted`): only the caller of `DemotePrimary` decides whether it serves again.
  - **The exception: `InitPrimary`.** It bootstraps a group of one member, waits for its election to end, and makes MySQL writable before its `changeTypeLocked` decision: it must create the sidecar database, and its caller (`InitShardPrimary`, or the first `PlannedReparentShard` of a shard that never had a primary) writes the reparent journal to it right after. The decision then refuses to serve: the new incarnation is recorded only once `InitPrimary` returned, and the other voters join afterwards. MySQL stays writable meanwhile, but vtgate does not route to the tablet until it serves, and the fence check leaves it alone: the group never had the voter majority, and its unrecorded incarnation is one that the tablet bootstrapped within `groupReplicationBootstrapGrace` (see "What it never fences"). Only clients that write to that MySQL directly can commit there, on a shard that is being initialized, and the caller holds the shard lock throughout.
  - **The cost.** A failover's new primary is promoted, and writable, once its election has ended rather than when it reports PRIMARY; the clear itself takes 30–110ms (sro-eval case B). Writes that clients send to a new primary's MySQL directly during the election now fail with errno 1290 instead of waiting; Vitess does not route there before the promotion.
- **Group shrink fails closed.** MySQL's view quorum counts only the members still in the view: after the other voters left the group (an expulsion, a clean shutdown, `unreachable_majority_timeout`), a primary alone in its view has quorum and keeps committing, and those commits exist on one voter only. Under a group replication policy with listed voters, a PRIMARY tablet whose group view holds fewer than a majority of the voters stops serving (reason `replication group lost the majority of its voters`), keeps its type so that vtgate buffers, and serves again once the majority is back. When the view shrinks under a primary that had the majority in that incarnation, the fence check notices within about 150ms, rather than the sync loop within `--group-replication-sync-interval`: it makes MySQL `super_read_only`, which also refuses the clients that write to MySQL directly, and then stops serving through the same not-serving reason (in G11, 72 writes routed by vtgate were acknowledged on a single voter within 0.68s before). The primary serves again, writable, only from a decision that the serving invariant holds, under the action lock (see "Fence check"). This is the same trade-off as a semi-sync primary without an acker: writes block rather than become durable on a single server. Such a tablet does not write heartbeats either (`--heartbeat-enable`): its query service still runs as a primary, and its heartbeats would be committed on a single voter. A PRIMARY tablet also stops serving, for the same reason, before its MySQL bootstraps a group: the new group has one member, which Group Replication used to make writable right away; it now stays read-only until the tablet decides that it may serve. While the tablet's MySQL is not a group primary (for example during that bootstrap), the reconcile loop leaves the not-serving state as it is, and `UndoDemotePrimary` is refused unless the serving invariant above holds. It does not apply while a shard is being converted (the shard's policy is not a group replication policy yet), when the group grows from one member while the primary keeps serving with semi-sync.

### Group configuration, derived from topo

Apart from the voters and the group incarnation, nothing new is stored in topo:

- **Group name.** A UUIDv5 of `keyspace/shard` in a fixed Vitess namespace, the same on every tablet of the shard. After a reshard the new shards get new groups automatically.
- **Communication stack.** Always `group_replication_communication_stack=MYSQL`: members connect to each other through MySQL's own port, authenticated as the replication user and secured like any other MySQL client connection. There is no separate group communication port, allowlist or XCom TLS configuration. MySQL deprecates the XCom stack in 9.7.2 and makes `MYSQL` the default in 26.7. Every member of a group must use the same stack; a group bootstrapped with XCom cannot be joined, and has to be restarted from scratch.
- **Enabling.** `--enable-group-replication` (default off) enables GR support on the tablet. `FullStatus` reports it (`group_replication_enabled`), which the migration preflight checks.
- **Local address.** The tablet record's MySQL address, `<mysql hostname>:<mysql port>`: the address other tablets replicate from.
- **Seeds.** The MySQL addresses of the other tablets of the shard, read from topo each time the tablet (re)joins. Non-voters are harmless seeds: a joiner only needs one reachable member.
- **Credentials.** The MySQL stack authenticates the connections between members, as well as distributed recovery, with the credentials stored on the `group_replication_recovery` channel; credentials given to `START GROUP_REPLICATION` would only be used for recovery. The tablet stores the existing replication user's credentials there (`CHANGE REPLICATION SOURCE TO … FOR CHANNEL 'group_replication_recovery'`) before each join, as it does on the default channel for asynchronous replication, with `group_replication_recovery_get_public_key=ON` or TLS. The replication user needs `GROUP_REPLICATION_STREAM` for these connections and `CONNECTION_ADMIN`, without which MySQL expels a member placed in `offline_mode`. `config/init_db.sql` grants both to `vt_repl`; existing deployments grant them on the shard primary before the migration. The tablet checks `mysql.global_grants` before it configures a join and refuses with `FAILED_PRECONDITION`, naming the `GRANT` to run, rather than letting MySQL refuse the connections and the join fail only after its timeout.
- **Tunables** (vttablet flags, applied with `SET GLOBAL` before each start):
  - `consistency`, default `BEFORE_ON_PRIMARY_FAILOVER`: a new primary applies its backlog before it serves.
  - `exit_state_action`, default `READ_ONLY`. `OFFLINE_MODE` (MySQL 8.4's default) is supported: MySQL then also sets `offline_mode` on a member that leaves its group involuntarily, which refuses vttablet's app, allprivs and filtered users (not the replication user, which has `CONNECTION_ADMIN`), so a partitioned old primary stops answering reads when the member leaves its group. MySQL never clears it; the tablet does, once the member is ONLINE in the legitimate group with a majority of the voters in its view, when it bootstraps the group, and when it makes MySQL the writable primary or an asynchronous replica. It is not the default: it also refuses VReplication's filtered user and any other user without `CONNECTION_ADMIN`, so a member that is only briefly out of its group stops serving and breaks its streams until it rejoins, and Vitess must clear a flag that MySQL never clears. With `READ_ONLY`, Vitess fences a member that left its group the way it fences any replica: MySQL is `super_read_only`, and replica reads are bounded by the tablet's replication lag tracking, with heartbeats or by polling (see "Replica reads and replication lag"). Primary reads are not: vtgate keeps sending them to the old primary until it follows the new one, about 0.6–2s after the group's election (1–13 reads answered after the election per failover in the G3E chaos scenario, at this test's read rate). With the 2s unreachable majority timeout below, OFFLINE_MODE does not avoid them either (0–4 per failover); it only did with 1s. The chaos tests do not separate the two actions on availability (see "Exit state action" and "Unreachable majority timeout sweep" in `doc/failover-audit/GroupReplication.md`).
  - `autorejoin_tries`, default 0. The tablet rejoins an expelled member itself, once the shard's legitimate group is active on another tablet. MySQL's own auto-rejoin does not check that: in the chaos tests an attempt blocked the member for about a minute (its status queries hung, and every change was refused) and could end in a group of its own.
  - `group_replication_start_on_boot` is persisted OFF. vttablet decides when to join, as it does for async replication (`skip_replica_start`).
- **Fixed settings.** Vitess always applies these three, because its design depends on them. They are not flags.
  - `member_expel_timeout=0`. The group replaces a failed primary about 7s after it fails. On MySQL 8.4.11, any value from 1 to 10s delays the expulsion, and so the election, by about 16s. The tablet rejoins expelled members on its own, so an expulsion caused by a short stall is cheap.
  - `paxos_single_leader=ON`. The primary is the group's only consensus leader, so a slow or failed secondary does not delay commits. MySQL applies it when a group is bootstrapped and refuses a joiner whose setting differs from the group's (verified on 8.4.11), so it must be the same on every member. A group that was not bootstrapped by Vitess with this setting cannot be joined; it has to be restarted from scratch first.

  - `unreachable_majority_timeout=2`. A member cut off from the majority of its group cannot commit: MySQL blocks its transactions until a majority certifies them. After 2s it rolls them back, leaves the group and becomes `super_read_only` (and `offline_mode` under `OFFLINE_MODE`), without Vitess acting. With 0 it stays in its minority forever, its commits blocked. The value is a race with the group's own repair: when a group of two loses a member while a third one is joining, the remaining member finds itself without a majority 5s later (the joiner is not in its view yet), and the group survives only if it expels the lost member, with the joiner's vote, before the timeout. That expulsion takes up to about 2s: the joiner's group communication thread blocks for 1s at a time trying to connect to the lost member, and MySQL notices the restored majority on its next one-second check. In the chaos tests, a voter rejoining after a restart while the primary's cell was cut off kept the group's majority in 10 of 18 races with 1s, 19 of 22 with 2s and 17 of 18 with 3s, and the flapping-partition scenario S7d lost its majority in 9 of 10 runs with 1s, 2 of 10 with 2s and 2 of 10 with 3s; a lost race costs 28–78s without writes, and with 1s the joiner sometimes ended alone in the old group's configuration, in ERROR for a minute. 2s and 3s cannot be told apart, so Vitess uses 2s. The cost is fencing that is 1s later than with 1s: a partitioned primary's clients wait about 7s, rather than 6s, for their commits to fail (a semi-sync primary blocks them 10–30s), and it becomes `super_read_only` 1s later. The election does not depend on it (see "Unreachable majority timeout sweep" in `doc/failover-audit/GroupReplication.md`). It does not replace the Vitess checks: a stale member alone in a new incarnation, or a primary whose group shrank through clean leaves, never sees an unreachable majority, and MySQL stays readable after it leaves (see Legitimate group and Group shrink).

  These settings matched Uber's RFC (#18648) until Vitess raised the unreachable majority timeout from 1s to 2s after the chaos results above.
- **Plugin.** It is loaded with `INSTALL PLUGIN` when needed. That survives restarts, needs no mysqld restart, and is not binlogged. Loading it through my.cnf (`plugin-load-add=group_replication.so`) is also supported.
- **Member action `mysql_disable_super_read_only_if_primary`: disabled.** By default Group Replication clears `super_read_only` on the member it elects primary, after every election: a bootstrap, a failover, `group_replication_set_as_primary`, and the election of a member alone in a group of its own. Vitess disables the action, so that **MySQL never makes a primary writable by itself: only a decision of the tablet that it may serve does** (see "Only Vitess makes MySQL writable"). The configuration of member actions belongs to the group while a member is in one, and to the member otherwise (`mysql.replication_group_member_actions`, with a version); a joiner takes the group's configuration, whatever its own version, and a group that a member forms on its own takes that member's (verified on MySQL 8.4.11, sro-eval case B). Every change needs `super_read_only` OFF; it is not binlogged out of a group, and takes no GTID in one.
  - **Locally, before every START.** `ConfigureGroupReplication` (`go/vt/mysqlctl/group_replication.go`), which every join and bootstrap runs before its `START GROUP_REPLICATION`, disables the action in the member's own configuration if it is enabled there, lifting `super_read_only` for the change like `INSTALL PLUGIN` (`read_only` stays ON) and setting it again. This covers fresh members, members that were out of their group when it was disabled online, members whose configuration was reset, and stray groups: in the lab, a joiner whose own configuration was still enabled formed a writable group of one and took 133 commits.
  - **Online, for groups bootstrapped before.** The serving, writable primary of a group checks the group's configuration once per incarnation, and every minute, and disables the action there if it is enabled (`disableSuperReadOnlyActionOnline` in the sync loop, under the action lock, on MySQL's status read under it). MySQL lets only the primary change the group's configuration; the members in the group take it within about a second, and the others when they join.
  - `mysql_start_failover_channels_if_primary` drives `SOURCE_CONNECTION_AUTO_FAILOVER` channels, which Vitess does not use; it is left enabled.
  - The migration back to semi-sync does not reset the action on the members that left the group. The asynchronous and semi-sync paths never consult it (only Group Replication's elections do), resetting it needs `super_read_only` OFF on each member, and the next migration to Group Replication disables it again before every START.

### Tablet (vttablet) behaviour

- **Startup** (`initializeReplication`). If the tablet is a voter (listed in the shard record):
  1. Configure GR and `START GROUP_REPLICATION` (join, never bootstrap).
  2. If the join fails because no member is reachable, retry in the background. Bootstrapping is never done from startup: two tablets could each create a group.
  3. `checkPrimaryShip` does not trust a stale PRIMARY record. The tablet starts as REPLICA, and the reconcile loop makes it PRIMARY if its MySQL is the group primary.

  Tablets that are not voters replicate asynchronously from the shard primary, as today.
- **Reconcile loop.** Every `--group-replication-sync-interval` (default 1s) the tablet reads its GR status:
  - If the member is the legitimate primary (see "The legitimate group"), and the tablet is not PRIMARY: promote the tablet record (`ChangeTabletType(PRIMARY)`). This yields a new `PrimaryTermStartTime`; the shard record follows through `shardSyncLoop`, and vtgate follows the new term.
  - If the member is active in a group of another incarnation than the recorded one: fence MySQL with `super_read_only` if it is that group's primary (the fence check has usually done it already), then leave that group. It rejoins the legitimate group like any other voter (below). The new group of the target of a live bootstrap intent is left alone (see "Foreign incarnation").
  - If the tablet is PRIMARY but the member is not the group primary, or has lost quorum: demote the record to REPLICA and stop serving. vtgate buffers or fails fast exactly as for a PRS. The tablet runs as a REPLICA right away; under the action lock it waits at most 1s for the topology to store its record, which otherwise follows in the background. Such a member is often one whose cell is cut off, topology server included, and the RPCs that bring its group back (VTOrc's bootstrap) need the action lock.
  - If the tablet is PRIMARY and its group view holds fewer than a majority of the listed voters, or belongs to another incarnation than the recorded one: stop serving, keep the type, and serve again once both hold, as MySQL reports it under the action lock (group replication policy only; see "Serving invariant"). When the view shrank under the primary, the fence check has usually stopped serving and fenced MySQL first; serving again lifts the fence. Before it stops serving for a lost majority, the loop reads the shard's durability policy again, which it otherwise caches for 10s: a migration back to semi-sync sets the shard's policy before it shrinks the group to the primary.
  - If the tablet is PRIMARY, a listed voter under a group replication policy, and its member is not in any group (`OFFLINE`, for example after mysqld restarted): demote the record to REPLICA without touching MySQL, so that vtgate stops routing to it and the next step rejoins it.
  - If the tablet is a voter but its member is `OFFLINE` or `ERROR`, and it is not in a backup or restore: rejoin with backoff, but only while another tablet reports an active member of the legitimate group. GR itself refuses a member with extra transactions.

  - On every run, it tells the query service whether MySQL is ONLINE in the shard's legitimate group, for replication lag polling (see "Replica reads and replication lag").

  This is how an unplanned failover elected by the group reaches Vitess within about a second, without VTOrc.
- **Fence check.** MySQL's view quorum only counts the members still in the view: a serving primary whose other voters left cleanly keeps quorum alone, and stays writable, since it was writable already. The reconcile loop notices such a group within `--group-replication-sync-interval`, and not at all while it runs a join itself, under the action lock. A second goroutine of the loop (`checkFence` in `group_replication_fence.go`) therefore watches MySQL more closely. Before Vitess disabled the member action `mysql_disable_super_read_only_if_primary`, MySQL also made the primary of every election writable, a stray group of one included, and the check fenced those too; MySQL now keeps them read-only by itself, and that branch of the check is defense in depth (see "What remains of the fence check" below):
  - **When.** Every 150ms (`groupReplicationFenceCheckInterval`) while it is armed: on a PRIMARY tablet; while MySQL is fenced; while a join or a bootstrap of the tablet's MySQL runs, whoever asked for it (the reconcile loop, the tablet's startup, `StartReplication`, `StartGroupReplication` for VTOrc's `GroupMemberNotOnline` and `GroupNotBootstrapped` and for the migration); and for 30s after one ended (`groupReplicationJoinWatchWindow`), a minute after one that failed, since MySQL keeps running a `START GROUP_REPLICATION` whose client gave up. Otherwise it reads nothing.
  - **What it reads.** One query (`readGroupReplicationFenceStatus` in `go/mysql/group_replication_fence.go`): whether the plugin is active, MySQL's `server_uuid`, `super_read_only` and view id, and the members of its view (`performance_schema.replication_group_members`), from in-memory tables. While one of the tablet's `START GROUP_REPLICATION` runs, the query leaves out the view id: when the `START` forms a group, or is admitted to one, `performance_schema.replication_group_member_stats` answers only once the `START` returns, about a second after `replication_group_members` lists MySQL as ONLINE, as the primary of the group it formed. During a `START` that finds no group, it answers at once, with no row (sro-eval case A). The check then decides on the members alone: a join into the shard's group never makes the joiner its primary, so a view of which MySQL is the primary and that lacks the voter majority is a group of its own, or one that every other voter left. It reads neither the topology nor another tablet, and does not take the action lock: it decides on the shard record and the durability policy that the tablet read last (the shard's own policy in that record first). It never makes MySQL writable, nor the tablet serve.
  - **What it fences.** MySQL, as the ONLINE primary with quorum of a view, under a group replication policy that lists voters, in three cases. A stray group: the view's incarnation is not the recorded one and the view holds fewer than a majority of the voters (any tablet type). A shrunk or superseded group, on a PRIMARY tablet: the check saw MySQL as the primary of a view with the voter majority in this incarnation, and the view now holds fewer than a majority of the voters, or the shard record lists another incarnation. And, while the fence holds, either condition keeps it: Group Replication clears `super_read_only` when it elects a primary, so the check sets it again. A view that holds enough members for a majority, but whose voters the tablet cannot all identify (by `server_uuid`, or by the MySQL address of their tablet record), is left to the reconcile loop, which asks the voters for their `server_uuid`.
  - **What it never fences.** A member of the recorded group that may serve. A group in the recorded incarnation that never had the voter majority, such as one just bootstrapped that the other voters are about to join: `InitPrimary` makes it writable once its election ended, and `PlannedReparentShard` writes its reparent journal to it, before the other voters join. A group that the tablet is bootstrapping, or bootstrapped within `groupReplicationBootstrapGrace` and whose incarnation is not recorded yet: once it is recorded, its shrink is fenced like any other, even within that minute (the migration's bootstrap and VTOrc's recoveries are followed by joins and leaves within seconds). The new group of the target of a live bootstrap intent (see "Foreign incarnation"). Anything during a planned pause of the primary (see "The migration's pauses and vtgate's buffer"), which serves again once MySQL is writable.
  - **How.** `SET GLOBAL super_read_only = ON` first, with a `lock_wait_timeout` of 1s: a write statement that is still running holds it back until it ends, and the check retries on its next run rather than wait. Then, on a PRIMARY tablet, the not-serving reason of the serving invariant (`replication group lost the majority of its voters`, or `MySQL's replication group is not the incarnation recorded in the shard record`), which is a new not-serving decision. Then it wakes the reconcile loop, with a fresh read of the shard record and the policy, which confirms the decision against the topology and leaves a foreign group. A tablet of another type gets no not-serving reason, which its reconcile loop would clear: its promotion decides.
  - **Lifting the fence, and making MySQL writable.** Only a decision that the tablet may serve as PRIMARY, under the action lock, on MySQL's status read under it, makes MySQL writable, right before the tablet serves: `serveAgain`, every promotion through `changeTypeLocked`, `UndoDemotePrimary`, the end of a planned pause and `SetReadWrite` (see "Only Vitess makes MySQL writable"). `liftGroupReplicationFenceLocked` makes MySQL writable whenever it is read-only, fenced by the check or left `super_read_only` by Group Replication's election, and the decision allows; it redoes the prepared transactions if the tablet became PRIMARY without serving. A promotion that the serving invariant refuses keeps MySQL read-only, and the tablet becomes a PRIMARY that does not serve. A decision that read MySQL's status before a newer fence does not lift it (see "Ordering" below). The reconcile loop also lifts the fence of a PRIMARY once it reads a durability policy that is not a group replication policy (see below). Joining or leaving a group hands `super_read_only` back to Group Replication and to the RPC that changes the group.
  - **Ordering with the action lock.** The check runs while the holders of the action lock change MySQL, so a small mutex (`groupReplicationFence.mu`, never held across a topology read or while waiting for the action lock) orders the two, with two counters. Each join, bootstrap and leave of MySQL's group starts a new *epoch*: a fence decided on a status read in an earlier epoch is dropped, and a join or a bootstrap waits for a `SET` that the check has in flight (at most 2s), so that a fence never lands on a group that Group Replication made writable after the check read MySQL. Each fence is a new *decision*: `serveAgain`, every promotion and `UndoDemotePrimary` take a snapshot of the decisions before they read MySQL's status, and do not make MySQL writable if a fence was decided since; once they made it writable, they record that MySQL is not fenced only if still no fence was decided, under the mutex, and otherwise set `super_read_only` again, keep the tablet from serving for the fence's reason, and `UndoDemotePrimary` fails (`FAILED_PRECONDITION`). Since the check decides and sets `super_read_only` under the mutex, MySQL ends up fenced whichever comes first, and a fence is never undone by a decision that started before it.
  - **An out-of-date policy.** The migration back stores the semi-sync policy as the shard's own before the first secondary leaves, and the primary then serves on as its group shrinks below the voter majority. When the view of a PRIMARY changes, the check makes the reconcile loop read the shard record and the policy again: with every voter in the group at the start, which the migration's preflight checks, the first leave keeps the majority and refreshes the policy before the second one. A fence decided under an out-of-date policy is lifted on the reconcile loop's next run, about a second later, at the cost of a pause of the primary.
  - **VTOrc.** A fenced PRIMARY is read-only, as is any PRIMARY whose MySQL may not serve. VTOrc's `PrimaryIsReadOnly` and `PrimaryCurrentTypeMismatch`, whose recovery calls `UndoDemotePrimary`, match under a group replication policy only on the primary of the shard's legitimate group (`IsLegitimateGroupPrimary`): the tablet refuses `UndoDemotePrimary` elsewhere, and VTOrc used to log a failed recovery every few seconds. On the legitimate primary, they stay the backstop that makes MySQL writable through the serving invariant. The Group Replication analyses of the same tablet have the same priority and come first, so they still run.
  - **Verified on MySQL 8.4.11** (raw lab of three instances, MySQL communication stack, outside Vitess): the primary of a group accepts `SET GLOBAL super_read_only = ON`, and then refuses commits with errno 1290, for the application user and for root. Joins, leaves and view changes leave it set (views 3 to 7: a secondary leaving and rejoining, which recovers from the fenced primary; 15s in a view of two; 15s alone in a view of one, still refusing commits); `STOP GROUP_REPLICATION` keeps it set. An election clears it: the bootstrap of a group of one by a member that was `super_read_only` before its `START`, and `group_replication_set_as_primary`, which also leaves the demoted primary `super_read_only`. The check sets it again after an election it must not accept. With a transaction open, the `SET` takes 17–19ms and the transaction's commit then fails; a write statement that is running blocks it until `lock_wait_timeout`. The check's query returns the expected rows on a member that never started Group Replication (plugin active, no member), on the primary of one and of three members, on a secondary, and after `STOP` (its own row, `OFFLINE`, empty view id). During a `START` that bootstraps a group (1.2–1.6s), the member is ONLINE PRIMARY with `super_read_only` off in `replication_group_members` about 0.6s after the `START` began, but every read of `replication_group_member_stats` waits until the `START` returns (up to 0.96s); the query without the view id answers in 13–63ms throughout.
  - **What remains of the fence check.** With the member action disabled, MySQL keeps the primary of every election read-only, a stray group of one included (0 commits in 2 lab runs, sro-eval case B; 0 writable stray windows in the G12 chaos runs, see "Audit: only Vitess makes MySQL writable"). The check is still needed for the shrink case: a serving primary is writable already when its view shrinks below the voter majority, and nothing in MySQL fences it. Its stray-group branch (an unrecorded incarnation without the voter majority, any tablet type), the reads during the tablet's own `START`s without the view id, and the exemptions for a bootstrap in progress, a recently bootstrapped group and a live bootstrap intent are defense in depth now: against a member whose local configuration could not be disabled before its `START`, a group that a component outside Vitess bootstrapped, or an operator who enabled the action again. They could be removed once a release has run with the action disabled everywhere; the shrink branch (a PRIMARY that saw the voter majority in this incarnation) stays.
- **RPCs on an active member:**

  | RPC | GR behaviour |
  |---|---|
  | `InitPrimary` | Bootstrap the group on this tablet (shard must have no active member; caller holds the shard lock), then as today. |
  | `PromoteReplica` | `group_replication_set_as_primary(own uuid)`; wait for role PRIMARY and the end of its election; change type, whose serve decision makes MySQL writable if the tablet may serve. No `RESET REPLICA ALL`. |
  | `DemotePrimary` | Stop serving and set `super_read_only`, as today; skip the semi-sync steps. A demotion that fails after it stopped serving or set `super_read_only` reverts through the same decision as `UndoDemotePrimary` (`revertDemotionWithGroupDecisionLocked`): wait for the end of a primary election, take the fence snapshot, decide on MySQL's status under the action lock, make MySQL writable (redoing the prepared transactions) only if the tablet may serve and no fence was decided since, then settle the fence and serve. Otherwise the tablet stays PRIMARY, not serving and read-only, with the reason recorded, and the sync loop makes it serve once the decision allows it. A tablet without Group Replication, or in a shard whose policy does not use it, reverts as a semi-sync tablet does. |
  | `UndoDemotePrimary` | Only if the member is still the group primary, once its election ended; under a group replication policy with listed voters, only if the serving invariant holds (recorded incarnation, majority of the voters ONLINE), on MySQL's status read under the action lock. |
  | `SetReplicationSource` | No-op for the default channel; wait for the reparent journal or position; fix the tablet type. Refused on the group primary, whose request can only be stale, except for a reparent's request (with a reparent journal entry): PRS repoints the old primary while the primary-elect switches the group's primary, so it waits until the group moved the primary away. |
  | `StartReplication` / `StopReplication` | Join or leave the group. |
  | `SetReadWrite` (`read_only=OFF`) | **Refused unless the member is the group primary,** its election ended, and, under a group replication policy with listed voters, the serving invariant holds. A GR secondary with `super_read_only=OFF` accepts writes and replicates them to the group; this was verified in the lab. |
  | `StartGroupReplication(bootstrap)` / `StopGroupReplication` (new) | Explicit membership control, used by VTOrc and the migration. A bootstrap request may carry checks, each optional: a GTID set that MySQL must have executed (the tablet applies its relay log first; see "The bootstrap candidate"), and the token and expected incarnation of its bootstrap intent (see "Bootstrap intent"); a check that fails refuses the bootstrap with `FAILED_PRECONDITION`, before MySQL's `START`. A refusal for a missing transaction, decided while MySQL is in no group and runs no `START`, is definitive, and the tablet reports it in the response (`definitive_refusal`) when the request asks for it (`report_definitive_refusal`; see "Bootstrap intent"). `StartGroupReplication` first stops the async channel and afterwards clears it (`RESET REPLICA ALL`): GR refuses to start while the channel runs, and a leftover channel can be resurrected later. A bootstrap suspends the tablet's rejoins while it runs, and stops a `START GROUP_REPLICATION` still in progress (`errno 3724`, or a member RECOVERING without any ONLINE member) first: MySQL refuses that `STOP` with errno 3663 ("Another instance of START/STOP GROUP_REPLICATION command is executing") until the `START` ends, for up to about a minute, so the tablet tries again every second for at most 10s (`groupReplicationStopOngoingStartTimeout`) and then fails with `UNAVAILABLE`. `mysqlctl` never sets `group_replication_bootstrap_group`, which MySQL accepts during a running `START`, while `performance_schema.processlist` shows one. A join (`bootstrap=false`) on a PRIMARY tablet under a group replication policy with voters, whose MySQL is not an active member, is refused (`FAILED_PRECONDITION`): the tablet demotes itself first (a stale primary), and a join would hold its action lock for up to a minute meanwhile. On a PRIMARY tablet under a group replication policy with several voters, it first stops serving (see "Group shrink fails closed"). On a PRIMARY tablet that still serves, as during a migration, it pauses serving around MySQL's start (see "The migration's pauses and vtgate's buffer"); `StopGroupReplication` does the same on a serving primary that leaves its group. Its topology reads (the durability policy, the voters, the tablet records for the seeds) wait at most 1s when the tablet read the same data before, and it then uses what it read last: VTOrc may reach a tablet whose own topology server does not answer, and the reads only give the member weight, the seeds and the number of voters. |
- **Semi-sync.** `fixSemiSync` treats an active group with at least two ONLINE members as sufficient durability. It then disables semi-sync and does not open the semi-sync monitor.
- **No default channel on a member that is not active.** A tablet whose MySQL is a group member replicates through its group, which it rejoins through the reconcile loop or VTOrc, and never on the default channel next to it. Two tablet paths used to configure it on a member whose MySQL was not active: the end of a primary term found in the shard record (`endPrimaryTerm`, the sweep's S7c r2 and S2), and the end of an offline backup. Both now apply one rule: under a group replication policy, a voter, or while no voter is listed a tablet that the policy allows in the group, configures no replication (the step-down demotes MySQL and changes the type to REPLICA), and so does a tablet whose shard's policy cannot be read (at the step-down, on a vttablet that runs Group Replication). A tablet that is not a voter, a former primary included, replicates from the group's primary, as such tablets do.
- **`InitPrimary` without `--enable-group-replication`** is refused in a shard whose policy uses Group Replication: the tablet would skip the bootstrap and make MySQL writable without a group.

### PlannedReparentShard

The orchestration is unchanged. The GR meaning comes from the tablet RPCs:

1. Preflight: the new primary must be a listed voter and an ONLINE member of the same group, and incarnation, as the current primary, and that group must be the shard's legitimate group (the recorded incarnation, a majority of the voters ONLINE); otherwise PRS fails with `FAILED_PRECONDITION` and names the voters. A tablet that is not a voter cannot be promoted while the group is active; swapping it in for a voter is future work. Without `--new-primary`, the election only considers the voters.
2. `DemotePrimary(old)` stops serving, so vtgate buffers. If it fails after it stopped serving or set `super_read_only`, its revert makes the old primary writable and serving only on the serving invariant (see `DemotePrimary` under "Tablet (vttablet) behaviour"), and PRS fails.
3. `WaitForPosition(new, pos)`.
4. `PromoteReplica(new)` runs `group_replication_set_as_primary`, which waits for in-flight transactions and leaves the old primary `super_read_only`. Once the election ended, the new primary's tablet makes MySQL writable, and serves (see "Only Vitess makes MySQL writable").
5. `SetReplicationSource` on the other members is a journal wait. The async replicas are re-pointed as today.
6. `PopulateReparentJournal(new)`.

The initial promotion of a shard that never had a primary selects the voters, with the primary-elect among them, and stores them in the shard record under the shard lock before `InitPrimary` bootstraps the group. Once `InitPrimary` returns, it records the new group's incarnation. Before anything changes, the primary-elect and every tablet that the policy allows as a voter must report `group_replication_enabled` and `shard_durability_policy_supported` (`CheckGroupReplicationCapabilities`, which `InitShardPrimary` also runs), and the primary-elect of any PRS must report `group_replication_enabled` (see "Upgrade requirement").

VTOrc bootstraps the group of a new shard on its own (`GroupVotersOutOfDate`, then `GroupNotBootstrapped`), and until a majority of its voters joined, no tablet is PRIMARY and the shard record has no primary term: a PRS that takes the shard lock in between takes the initial promotion path, and its `InitPrimary` would bootstrap a second group and record its incarnation over VTOrc's. Under a group replication policy, the initial promotion therefore fails with `FAILED_PRECONDITION`, before it changes anything, when the shard record holds a live bootstrap intent (a bootstrap runs or ran, its incarnation not recorded yet), or a recorded incarnation, or when any tablet's MySQL is an active member of the shard's group (`checkShardHasNoGroup`). The error tells the operator to wait until VTOrc made the group's primary PRIMARY and run PRS again. A tablet whose MySQL is an active member of another group (another group name) also fails the initial promotion, with its own error: `InitPrimary` could neither bootstrap the shard's group on it nor make it join, and the operator has to stop Group Replication on it. The intent covers VTOrc's bootstrap RPC that timed out while MySQL's `START` still runs, before any tablet reports a member; the active member covers a group whose intent expired before its incarnation was recorded (the TLA+ model's `init_orc_vgtid` violates a guard on the intent alone). The GTID sets do not reveal VTOrc's group: on MySQL 8.4.11, with `group_replication_view_change_uuid` at its default `AUTOMATIC`, a bootstrap and a join log no view-change GTID (raw lab of three instances).

### EmergencyReparentShard

The group fails over by itself when a majority survives. ERS in GR mode must uphold the rules in `EmergencyReparentShard.md`: certainty, time-bound stages, shard lock re-checks, reparent journal, and no errant GTIDs.

1. Lock the shard and collect `FullStatus` from all tablets, time-bound.
2. If a reachable member reports that it is ONLINE, PRIMARY and has quorum, in the shard's legitimate group (recorded incarnation, majority of the voters ONLINE in its view), the group has already elected. Promote that tablet in topo (`PromoteReplica`, which is only a type change there) and write the reparent journal. If `--new-primary` names another member, follow with a PRS-style switch. Tablets that are not voters are re-pointed as async replicas; voters that are not active are left to rejoin the group.
   Only a listed voter becomes the shard's primary, as only a voter serves: if the group elected a member that is not a voter, ERS makes an eligible voter the group's primary instead, and a `--new-primary` that is not a voter is refused with `FAILED_PRECONDITION`. The same holds for a member whose vttablet does not run Group Replication (`group_replication_enabled` unset), which would serve without the serving invariant.
3. If no reachable member has quorum, ERS fails, unless the operator passes `--group-replication-force-quorum` (not implemented in the prototype). That choice needs a human, like `--allow-split-brain-promotion`: it would pick the member with the most advanced *received* GTID set and use `group_replication_force_members`. Even that member may lack transactions that a majority accepted and the old primary acknowledged (see "What an acknowledged commit guarantees"), which is why it needs a human.

### VTOrc

VTOrc keeps its single loop. Discovery reads `FullStatus.group_replication_status`, and analysis gains GR codes:

| Analysis | Condition | Recovery |
|---|---|---|
| `GroupPrimaryNotInTopo` | A member is the legitimate primary of the shard's group, but its tablet is not the topo primary (for example, the tablet-local loop failed). | Confirm with fresh statuses, then `PromoteReplica` on that tablet (type change) plus journal; refused if its vttablet does not run Group Replication (`group_replication_enabled` unset). If the topology server of that tablet's cell does not answer, move the group primary instead (see below), to a member whose vttablet runs Group Replication. |
| `GroupMemberNotOnline` | The tablet is a voter, not PRIMARY in the topology or in its own state (the tablet demotes a stale primary itself first), it is OFFLINE or ERROR without a `START` in progress, and another tablet is an active member of the legitimate group with quorum. | Confirm with fresh statuses (at most 2s) under the shard lock, then `StartGroupReplication(bootstrap=false)` in the background, once the lock is released: a join does not need it, and can block for as long as the RPC's timeout. One join per tablet runs at a time. Runs whether or not the shard has a primary tablet. Not while the shard record lists no incarnation (see "Joining"). |
| `GroupNotBootstrapped` | GR policy, no member of the shard is active or runs a `START GROUP_REPLICATION` that VTOrc observed for less than 10s, and all voters are reachable (see "What an acknowledged commit guarantees"). | Record a bootstrap intent, refused while another tablet's intent is recent; `StartGroupReplication(bootstrap=true)` under the shard lock on a voter whose executed and received set contains every voter's (see "The bootstrap candidate"), with the required set, the intent's token and the incarnation it expects, which the tablet checks right before MySQL's `START`; record the new group's incarnation (compare-and-swap), or adopt it if the RPC failed, or withdraw the intent if the tablet refused definitively (see "Bootstrap intent"); and make the other voters join it (in the background). A live intent for a voter that is no longer the candidate, but answers, in no group and without a `START`, gets its own bootstrap sent to that voter again first; after a definitive refusal, VTOrc withdraws it and bootstraps the candidate in the same pass (see "Bootstrap intent", a stale intent). |
| `GroupBootstrapNotRecorded` | The tablet is the target of the shard's bootstrap intent, and its MySQL is the ONLINE primary, with quorum, of a group of another incarnation than the recorded one: a bootstrap whose reply was lost. | Re-read the shard record and the tablet's status under the shard lock, adopt the group if the conditions of "Bootstrap intent" hold (compare-and-swap of the incarnation, which clears the intent), and make the other voters join it. Runs without a shard primary tablet. Also matches the primary of a group while the shard record lists no incarnation and holds no intent for it (`adoptUnrecordedGroup`): VTOrc records it only when it is the only group the shard can have, which is what its own bootstrap on that member would create: no bootstrap intent is live, every voter answers, no tablet runs a `START` or is active in another incarnation, and the primary executed every transaction that a voter executed or received. The write is a compare-and-swap on the empty incarnation and the absence of a live intent. |
| `GroupVotersOutOfDate` | VTOrc's stored state proposes a change of the voters (see "Voters"): the initial list of a shard without a group, SwapVoter for a voter unreachable for `--group-replication-voter-replacement-grace-period` (default 1m) or whose tablet record was deleted, GrowVoter for a cell with an eligible tablet and no voter, RemoveVoter for a deleted voter without a spare, RemoveVoterNoGroup for a deleted voter while no group runs. | Decide the change on one fresh read under the shard lock (the shard record and every tablet's `FullStatus`, 2s each), with its preconditions (P1, P2, P3), and write it as a compare-and-swap on the list and the incarnation read, with nothing in between; then the new voter joins the group. |
| `GroupPrimaryNotVoter` | The primary of the shard's legitimate group is not a voter. | Move the group primary to an ONLINE voter of its view (`PromoteReplica`), on one fresh read under the shard lock. |
| `GroupVotersBelowTarget`, `GroupVoterUnreplaceable`, `GroupVoterRecordDeleted` | Fewer voters than cells with an eligible tablet, or fewer than three; a failed voter without a valid spare; a deleted voter still active in the group, or in the primary's view without a spare. | None: alerts. |
| `GroupQuorumLost` | Members are reachable, but none has quorum. | None; alert (ERS with an explicit force flag is the operator path). |
| `GroupCellMajority` | `group_replication_cross_cell`, and one cell holds a majority of the ONLINE members. | None; alert. |

For tablets that are active members, the async analyses are suppressed:
- `ReplicationStopped`
- `NotConnectedToPrimary`
- `ConnectedToWrongPrimary`
- `ReplicaMisconfigured`
- `PrimaryHasPrimary`
- the semi-sync `*MustBeSet` / `*MustNotBeSet` codes
- `PrimaryIsReadOnly` while the member is not the group primary

Under a group replication policy, `PrimaryIsReadOnly` and `PrimaryCurrentTypeMismatch` only apply to the primary of the shard's legitimate group: Group Replication leaves every primary it elects read-only, and the tablet refuses `UndoDemotePrimary` until the serving invariant holds.

`StaleTopoPrimary` (a PRIMARY tablet with an older term than the shard's primary) only fixes the tablet type of a listed voter under a group replication policy: the voter rejoins its group, and configuring the default channel on it would start asynchronous replication next to the group (NEW-3 of the audit). Other tablets are still made asynchronous replicas.

The same holds for the asynchronous replica analyses (`NotConnectedToPrimary`, `ReplicationStopped`, `ConnectedToWrongPrimary`, `ReplicaMisconfigured`, `ReplicaSemiSyncMustBeSet`, `ReplicaSemiSyncMustNotBeSet`), whose recovery (`fixReplica`) points the default channel at the primary: under a group replication policy they do not match a voter, active or not, nor any tablet that the policy allows in the group while no voter is listed (`replicatesThroughGroup`). In the G13 chaos run, a voter whose join was in flight (so `GroupMemberNotOnline` did not match) matched `NotConnectedToPrimary`; three VTOrcs ran `fixReplica` on it, and once the member was back in its group the replication lag poller read the default channel and the member served no replica reads. `fixReplica` checks it again itself: on a voter it only makes MySQL read-only (`ReplicaIsWritable`), and never configures the default channel. Tablets that are not voters keep the analyses.

A voter that `GroupMemberNotOnline` applies to is not analyzed for `ClusterHasNoPrimary` or `PrimaryTabletDeleted`, which outrank it: a group that lost the majority of its voters has no primary that a reparent could follow, and only gets one once its voters rejoin. The failovers are still analyzed on the group's members.

**A group primary whose cell's topology server is down.** The group's election ignores the topology. A tablet writes its own record, in its cell's topology server, before it becomes PRIMARY, and VTOrc's `PromoteGroupPrimary` goes through the tablet: while that server does not answer, neither can promote the member the group elected, and the shard has no primary (NEW-4 of the audit: 104.6s in the G9b chaos scenario, 169.6s in S9b). `PromoteGroupPrimary` reads the shard's tablets cell by cell (`topo.GetTabletMapAndFailedCellsForShard`, 2s per cell), and when the group primary's cell is among the cells that did not answer, it makes another member the group primary instead:

- Under the shard lock, it re-reads the status of the tablets of the cells that answered. The members of the shard's legitimate group among them (recorded incarnation, a majority of the voters ONLINE in their view) must agree that the analyzed member is their primary. The group primary's tablet must not be PRIMARY in the shard record, nor in its own state if it answers within 2s; the move does not otherwise depend on that tablet.
- The target is an ONLINE voter in that view, in a cell that answered, that the durability policy allows to be promoted (as for a planned reparent): the highest member weight, then the lowest alias. VTOrc calls `PromoteReplica` on it, which runs `group_replication_set_as_primary` and makes its tablet PRIMARY, and writes the reparent journal. No RPC is added.
- It waits until the group primary has not been the topology primary for 5s (`groupPrimaryMoveGracePeriod`): a tablet promotes itself within one sync interval, the per-cell read already waited 2s for the cell, and a short unavailability of a topology server (an etcd leader election) does not move the primary. A member whose cell answers is never moved away from.
- A member that the group primary was moved away from is neither moved to nor moved away from again for a minute, so the primary does not go back and forth. Without an eligible target, or within that minute, VTOrc logs why and skips the recovery of that tablet for 10s (`GroupPrimaryMoveBackoff`) instead of failing it on every poll.
- The tablet that could not be promoted may still write its record later, if its topology server comes back during its attempt: its term is taken after it checked that its MySQL is the group primary, so it is older than the new primary's; its own state stays REPLICA, since making MySQL writable is refused on a group secondary; and `StaleTopoPrimary` fixes the record. A tablet that did become PRIMARY before the move demotes itself through the reconcile loop.

The GR recoveries of a single tablet also refresh the shard's tablet records cell by cell, keeping the records of the cells that do not answer, instead of waiting the whole remote operation timeout for them. G9b: the shard primary changed 22.2s and 20.4s after the primary died (104.6s before); S9b 23.3s when the group elected the member of the cut-off cell (169.6s before).

`DeadPrimary` in a shard whose members are active does not run ERS right away: the group elects on its own. VTOrc waits for `--group-replication-failover-grace-period` (default 30s) for `GroupPrimaryNotInTopo` to appear, and only then falls back to the ERS path described above.

### Replica reads and replication lag

A member that leaves its group under the `READ_ONLY` exit state action keeps answering reads. Its tablet stays a serving REPLICA, and replica reads from it are bounded by the tablet's replication lag tracking, like those of any replica: the tablet reports its lag to vtgate, vtgate stops routing replica reads to a tablet whose lag exceeds `--discovery-low-replication-lag` (unless fewer than `--min-number-serving-vttablets` tablets are below it), and the tablet stops serving once its lag exceeds `--unhealthy-threshold`. Both lag tracking modes work on the members of a group.

- **Heartbeat** (`--heartbeat-enable`), unchanged. The primary writes a heartbeat row every `--heartbeat-interval`; the group replicates it like any transaction; a secondary's lag is the age of the last heartbeat it applied. A member that no longer receives the shard's transactions (cut off, out of its group, alone in a group of its own) no longer applies heartbeats, and its lag grows from the moment it stopped receiving them.
- **Polling** (`--enable-replication-reporter`). The poller used to read only `SHOW REPLICA STATUS FOR CHANNEL ''`. A member has no default channel (the tablet clears it when MySQL joins a group), so the poller reported `no replication status` and every secondary of a group stopped serving, partitioned or not. The poller now understands Group Replication (`go/vt/vttablet/tabletserver/repltracker/poller.go`):
  - **Which path.** It still reads `SHOW REPLICA STATUS FOR CHANNEL ''` first. Only if MySQL has no default channel does it read the group state, and it only uses it if the Group Replication plugin is active. A tablet without Group Replication runs the same query as before and gets the same lag or error; so does an asynchronous replica of a group, or a tablet that is being converted to Group Replication, which still replicates through its default channel even if the plugin is loaded. Reading the group state first would make the plugin, rather than the channel that actually carries the tablet's transactions, decide where the lag comes from.
  - **One query** (`readGroupReplicationApplierStatus` in `go/mysql/group_replication_lag.go`): whether the plugin is active; the member's own state; how many members its view has, and how many of them it can reach; its view id; how many transactions wait for certification or in the applier queue (`replication_group_member_stats`); and the age of the oldest transaction the applier works on: `UNIX_TIMESTAMP(NOW(6))` minus the smallest original commit timestamp of the `group_replication_applier` channel's workers (`APPLYING_TRANSACTION_ORIGINAL_COMMIT_TIMESTAMP`, one row per parallel worker) and coordinator (`PROCESSING_TRANSACTION_ORIGINAL_COMMIT_TIMESTAMP`). It reads only in-memory `performance_schema` tables and `information_schema.PLUGINS`.
  - **Lag of a healthy member**: the age of the oldest transaction the applier works on, the first transaction the member has not applied; 0 when no transaction waits. On a GR member, MySQL sets a transaction's original commit timestamp on the member that ran it (the primary) when the transaction is ready to commit, before certification, and every member keeps it. When transactions wait but none has reached a worker or the coordinator yet (an instant: 1 of 300 reads under write load on MySQL 8.4.11), the poller reads again; if that does not tell either, it estimates the lag like an unknown `Seconds_Behind_Source`. An idle group has no lag at all, where heartbeats report up to one heartbeat interval.
  - **Healthy** means: MySQL reports the member `ONLINE`, reaching a majority of its view (both read in the same query, on every health check), and the tablet manager's group replication sync loop found it `ONLINE` in the shard's legitimate group (the recorded incarnation, quorum, a majority of the listed voters `ONLINE` in its view) less than 10s ago, in the incarnation that MySQL reports now.
  - **Out-of-group rule.** Any other member (`OFFLINE`, `ERROR`, `RECOVERING`, `ONLINE` without quorum, `ONLINE` in a group without a majority of the voters or of another incarnation) does not receive the shard's transactions, and its idle applier would report no lag forever. It is reported like a replica whose replication stopped: the time since it was last found healthy plus the lag measured then, so the thresholds above take it out of replica reads. A member that was never found healthy reports an error (`UNAVAILABLE`), as a replica that never replicated does, and does not serve. A member whose group state cannot be read counts as not healthy: MySQL blocks reads of these tables while a `START` or `STOP GROUP_REPLICATION` runs on it, for example VTOrc's attempts to make a cut-off member join. The read is bounded to 1s and not repeated for 5s after a failure, because the health check holds the query service's state lock, which queries wait for.
  - **Layering.** MySQL's own view tells whether the member is in a group and can reach its majority, but not whether that group is the shard's legitimate group: a group that shrank to one member, or a stray incarnation that a failed join formed, has quorum in its own view. That takes the shard record (incarnation, voters) and the voters' `server_uuid`s, which the tablet manager's sync loop already reads every second to decide whether to promote, leave a foreign group or rejoin. The sync loop therefore passes its verdict, and the view it is about, to the query service on every run (`tabletserver.Controller.SetGroupReplicationVerdict`, in-process; no RPC or proto change), and the poller combines it with what MySQL reports at the time of each health check. The poller does not trust a verdict about another incarnation than MySQL's current one, so a stray group that formed since the last run of the loop is not healthy; a verdict that the loop stopped renewing (a stuck or stopped loop) is not trusted after 10s. A member that left its group, or lost its majority, is noticed by the next health check, without waiting for the loop. The verdict counts the voters in the view by their known `server_uuid` or by the MySQL address of their tablet record, without asking the voters for their `server_uuid`s on the way (the loop does that in the background), so that the loop never waits for a cut-off voter.
- **Clock skew.** Both modes compare a timestamp taken on the primary with the secondary's clock: heartbeats with the clocks of the two vttablets, polling with those of the two mysqlds (the original commit timestamp against the secondary's `NOW(6)`). A skew shifts the reported lag by the skew; a secondary whose clock is ahead reports more lag, and one whose clock is behind reports less, down to 0 (the poller does not report negative lag). Keep the clocks synchronized. The time since a member was last healthy is measured with the tablet's own clock and does not depend on skew.
- **Heartbeat or polling.** In the G13 chaos scenario (a secondary cut off from the other members, still reachable by vtgate; `--discovery-low-replication-lag 5s`, `--min-number-serving-vttablets 1`, `--health-check-interval 1s`), the cut-off secondary answered its last replica read 7.1s after the cut with heartbeats and 10.1s after it with polling; all its answers in between were stale. Heartbeat lag grows from the moment heartbeats stop arriving. Polling only knows that a member is cut off once MySQL does: Group Replication suspects an unreachable member after about 5s (not configurable), and the member leaves its group 2s later. The lag of a cut-off member is thus underestimated by up to about 5s with polling, and stale replica reads last that much longer; with the default `--discovery-low-replication-lag` of 30s, about 35s rather than 30s. Polling needs no writes on the primary and costs one query per health check per tablet; heartbeats write a row on the primary every interval, which every replica applies. Heartbeats are preferable where replica reads must be fresh; polling is supported.
- **Thresholds.** `group_replication_cross_cell` with three cells has two secondaries per shard, and vtgate's default `--min-number-serving-vttablets` of 2 keeps both in replica reads whatever their lag, up to `--discovery-high-replication-lag-minimum-serving` (2h): a cut-off secondary then serves stale reads until its tablet's `--unhealthy-threshold` (2h by default). Lower `--min-number-serving-vttablets` to 1, or `--unhealthy-threshold`, to take it out sooner. vtgate only routes replica reads to the REPLICA tablets of its own cell or cell alias, and prefers those of its own cell; with one voter per cell, a vtgate's cell may hold only the primary.

### Other components

- **Lag.** Both heartbeat and polling lag tracking work on the members of a group; see "Replica reads and replication lag".
- **Status queries.** The MySQL flavors now read `SHOW REPLICA STATUS FOR CHANNEL ''` and filter `replication_connection_configuration` on `CHANNEL_NAME = ''`. On a GR member the plugin's own channels (`group_replication_applier`, `group_replication_recovery`) show up in those tables and used to break parsing (`query returned 2 rows`).
- **Group Replication status.** It is read from `performance_schema.replication_group_members`, `replication_group_member_stats` (view id), `replication_connection_status` (received set), `processlist` (a `START GROUP_REPLICATION` in progress), `threads` (`THD_primary_election_primary_process`, a primary election in progress) and the member's variables, including `group_replication_paxos_single_leader`. It does not read `replication_group_communication_information`: on a member expelled after a freeze, that query never returned and held a lock that the member's own rejoin needed, which wedged the member in ERROR (NEW-5 of the audit). The reads run with the caller's context, and the tablet bounds every read by 10s, so that a status query cannot hold the action lock indefinitely.
- **Backups.**
  - Online engines (xtrabackup, mysqlshell, clone) work on a member as is.
  - The builtin engine stops mysqld. The tablet leaves the group for the duration and rejoins afterwards through the reconcile loop.
  - A tablet restored from a backup joins with incremental recovery as long as the donors still have the binlogs, otherwise with clone.
- **Errant GTIDs.** Transactions of the group carry the group name as their UUID, which is identical on every member. VTOrc's errant GTID detection must compare against the group primary's executed set, including the group UUID. GR refuses to admit a member that has extra transactions anyway.
- **`sql_log_bin=0` writes** (`ExecuteFetchAsDBA --disable-binlogs`, TableGC purge, `ApplySchemaChange` without replication) create silent divergence under GR exactly as under async replication. No new risk, but worth documenting.
- **Schema requirements.** A preflight refuses the conversion when a user table lacks a primary key (or non-null unique key) or is not InnoDB. After conversion, `sql_require_primary_key=ON` is recommended. All `_vt` sidecar tables already have primary keys.

## Migration: semi-sync → Group Replication, online

`vtctldclient MigrateReplicationMode --durability-policy group_replication_cross_cell <keyspace>[/<shard>]` runs the steps below for each shard, under the shard lock. Every step is idempotent, so the command can be re-run after a failure; `--dry-run` prints the plan. Before the first shard is converted, the keyspace record names the target policy, and keeps the policy it converts from as its migration source, which applies to every shard until it is converted (see "The shard's policy during a migration").

The steps were validated on MySQL 8.4.11 with a continuous write load; bootstrapping and joining caused **0 failed writes**.

0. **Name the target policy in the keyspace record**, once per migration, before the first shard is converted. Every tablet of the keyspace that answers must first report that its vttablet resolves the shard's own policy and the migration source (`FullStatus.shard_durability_policy_supported`), not only the voters of the converted shards (a tablet that does not answer is logged: an older vttablet that starts later exits on the policy it does not know), and a dry run of the requested shards' conversion must pass, so that a migration that its preflight refuses leaves the keyspace record as it was. Then, in one write under the keyspace lock, `durability_policy` becomes the target policy and `migration_source_durability_policy` (field 13 of `Keyspace`) the policy it converts from. A component that knows the field resolves the same policy for every shard as before; one that does not reads the target policy for every shard (see "Upgrade requirement").
1. **Preflight.**
   - All tablets reachable; GTID mode ON; ROW binlog format.
   - MySQL ≥ 8.0.27, the first version with the MySQL communication stack; 8.4 is recommended because of its defaults (`BEFORE_ON_PRIMARY_FAILOVER`, `OFFLINE_MODE`, certification GC).
   - The voters are selected (`SelectVoters` for the target policy, with the current primary as the group's primary and any voters already in the shard record as the current list, so a re-run keeps them). There must be at least 3 and at most 9; under `group_replication_cross_cell`, which allows one voter per cell, that means eligible tablets in at least 3 cells. The error names the cells found.
   - Every user table has a primary key and is InnoDB.
   - Every voter runs vttablet with `--enable-group-replication`, and its tablet record has a MySQL port.
   - Every voter runs a vttablet that applies the shard's own durability policy (`FullStatus.shard_durability_policy_supported`); see "Upgrade requirement".
   - The replication user's privileges are not read here, since vtctld does not know the user: each tablet checks them before it configures its join, the primary first, before the bootstrap.
2. **Store the voters** in the shard record.
3. **Bootstrap on the current primary** (`StartGroupReplication(bootstrap=true)`), and **record the group's incarnation** in the shard record. Semi-sync stays enabled, and the async replicas keep acknowledging. While Group Replication starts, MySQL refuses a commit already under way (errno 3100, its `before_commit` hook), and the bootstrapped primary stays `super_read_only` until the tablet, once the election ended, decides that it may serve (the policy is not a group replication policy yet) and makes it writable (errno 1290 meanwhile). The primary therefore pauses: it stops serving before MySQL starts Group Replication and serves again, with its primary term, once MySQL is the writable primary of its group; vtgate buffers the writes meanwhile (see "The migration's pauses and vtgate's buffer"). The pause lasts about 1.35s, MySQL's `START GROUP_REPLICATION`.
4. **Join the other voters one by one** (`StartGroupReplication`). Each one stops its async channel, recovers incrementally from a donor, and becomes ONLINE. Cross-cell voters join first, so the group gets a cross-cell majority as early as possible.
5. **Disable semi-sync on the primary as soon as the group has two ONLINE members,** and before the last semi-sync acker leaves its async channel. With Vitess's infinite semi-sync timeout, losing the last acker blocks every commit; the lab reproduced this. Ackers that are not voters keep acknowledging until this point, so they count as remaining ackers while the voters join. From this point, the group provides durability: every commit waits for a majority of the members to accept it (see "What an acknowledged commit guarantees"). The "group supersedes semi-sync" rule makes the tablet and VTOrc agree.
6. Every other tablet becomes, or stays, an async replica of the primary, with semi-sync off. A tablet that is an active member but not a voter leaves the group first.
7. **Store the target policy as the shard's own policy** (`Shard.durability_policy`). From now on the shard is managed as a Group Replication shard, whatever the keyspace policy: VTOrc runs the Group Replication analyses and recoveries on it and none of the semi-sync ones that would undo the conversion, ERS and PRS take the Group Replication path, and its tablets apply the serving invariant, rejoin the group and take their member weight from it.
8. Once every shard of the keyspace is converted, **remove the keyspace's migration source**, under the keyspace lock, after checking again that every shard of the keyspace has the target policy as its own (a new shard's creation takes the keyspace lock too, and a shard created during the migration has the source policy until it is converted), and then **remove the shards' own policies**, which are the keyspace's from then on.

### Rollback: Group Replication → semi-sync

`MigrateReplicationMode --durability-policy cross_cell <keyspace>[/<shard>]` mirrors the conversion, shard by shard under the shard lock:

1. Preflight: the primary is the primary of the group, every member is in its group, the target policy's semi-sync ackers exist, and, while the keyspace has another policy, every member and voter runs a vttablet that applies the shard's own policy.
2. **Store the target policy as the shard's own policy**, before anything changes. From now on the shard is managed as a semi-sync shard: its primary re-enables semi-sync, and does not stop serving, as its group shrinks below a majority of the voters, and serves on its own once it left the group. Nothing changes immediately, because the active group supersedes semi-sync.
3. For each secondary: `StopGroupReplication`, then `SetReplicationSource(primary, semiSync=true)`. The primary enables semi-sync as soon as it has an eligible acker, and before its group shrinks below two ONLINE members.
4. On the primary: `StopGroupReplication` pauses the primary like the bootstrap does, clears `super_read_only`, which GR sets when it stops, applies the policy's semi-sync setting, and serves again with the same primary term. MySQL refuses commits for the whole `STOP GROUP_REPLICATION`, about 3.6s in the lab, which vtgate buffers.
5. Clear the voters and the group incarnation in the shard record once the last member left the group. A later conversion selects them afresh and records the incarnation of its new group.
6. Once every shard of the keyspace has left its group and has the target policy, set the keyspace durability policy, in one write that also removes a migration source left by an interrupted migration to Group Replication, and remove the shards' own policies. Until then the keyspace record names the Group Replication policy, so that no older component manages a shard that still runs its group by the semi-sync policy.

Before this design, the rollback set the keyspace policy first: every shard that was not converted back yet lost the Group Replication rules while it still ran its group, until its turn came.

### The shard's policy during a migration

A shard's durability policy (`topo.ShardDurabilityPolicy`: the shard's own policy if set, else the keyspace's migration source if set, else the keyspace's policy) changes only under its shard lock, at one fixed step of its own conversion. The keyspace record changes twice in a migration to Group Replication, and each write changes no shard's policy: step 0 names the target policy and keeps the policy it converts from as the migration source, and step 8 removes the source once every shard has the target policy as its own. Every other component therefore sees each shard switch at a single moment, the same for all of them up to their caches, and never during a step that needs the other policy:

- **Forward, at the end.** Before the switch, the rules of a group replication policy would fight the conversion. With a group of one member and three listed voters, the serving invariant makes the primary stop serving until two voters joined; the tablet's semi-sync rule (`SemiSyncAckers` is 0) makes the primary drop semi-sync before a second member acknowledges anything; the tablets would rejoin voters on their own, and VTOrc would join, bootstrap or replace voters under the migration's feet. After the voters, the bootstrap, the incarnation, the joins and the end of semi-sync, the shard runs exactly what the policy describes, so the switch is safe. The weight of the members that joined during the conversion is MySQL's default (the policy was not a group replication policy yet; see "Prototype scope").
- **Back, at the start.** The rules of the asynchronous policy must hold before the group shrinks below a majority of the voters (the primary must not fail closed, and must re-enable semi-sync), and before the primary leaves its group (it serves on its own, with semi-sync, instead of staying read-only).
- **Keyspace record.** From step 0 until step 8, the keyspace record of a migration to Group Replication names the target policy: the invariant is that the keyspace's `durability_policy` names a Group Replication policy whenever any shard of the keyspace may run a group. A rollback keeps it so until the last shard has left its group. An older component, which knows neither the migration source nor the shard's own policy, therefore never reads a semi-sync policy for a shard that runs a group (see "Upgrade requirement"). A migration to Group Replication and one back may run at the same time: the conversion to Group Replication checks that the keyspace record still names a Group Replication policy under the shard lock and again right before its bootstrap, once the shard's voters are stored, and the migration back's final keyspace write checks, under the keyspace lock, that no shard record lists voters, an incarnation, a bootstrap intent or a Group Replication policy of its own unless its own policy is the target. Either the migration back's write comes first, and the bootstrap is refused, or the voters do, and the write is refused. A single keyspace write was preferred over storing the old policy in every shard record and then switching the keyspace: a reader with a stale shard record and a fresh keyspace record (the tablet reads the shard record, then the keyspace's) would resolve the Group Replication policy for a semi-sync primary.
- **Partial and failed runs.** A run that fails before the forward switch leaves the shard on the migration source's policy, in the half-converted state the steps already handle; one that fails after the backward switch leaves it on the target policy, with its group partially shrunk, which the next run continues. A shard that runs its group but has no policy of its own (converted by an older version) is not counted as converted: running the migration on it again only stores its policy. The migration source is kept, and the step that keeps it names the shards that are not converted to the target policy yet. While it is set, `SetKeyspaceDurabilityPolicy` refuses any change: running the migration again finishes it, and the migration back to semi-sync reverses it.
- **End state.** Once the keyspace has the target policy and no migration source, the shards' own policies are removed (only those equal to the keyspace's; another one is kept, and reported). Keeping them would make a later `SetKeyspaceDurabilityPolicy` silently not apply to these shards. A run whose keyspace switch succeeded but whose removal failed leaves own policies that equal the keyspace's, which is harmless; the next run removes them.
- **Caches.** vtctld resolves the policy from the shard record it read under the shard lock, which the migration holds when it changes it. VTOrc refreshes the keyspace and shard records under the shard lock before every recovery, and analyzes again. The tablet's sync loop caches the policy for 10s, but drops it as soon as a shard record it reads (every 5s while its MySQL is in a group, and before every promotion) sets another own policy; before it stops serving for a lost voter majority, and in every RPC that changes the group, it reads the policy from the topology. In the forward direction a stale cache delays the Group Replication rules by at most 10s, which is how the switch behaved for the keyspace policy before; in the backward direction the shrink itself makes the primary read the policy again.

### Upgrade requirement

**vtctld, VTOrc and every vttablet must be upgraded to a version that knows the shard's own durability policy and the keyspace's migration source before a migration starts, and at least one upgraded VTOrc must run.** The design keeps one invariant so that a component that is not upgraded fails safe rather than managing a shard by the wrong policy: **whenever any shard of a keyspace may run a group, the keyspace's `durability_policy` names a Group Replication policy** (step 0 of the migration, and the rollback's order). What an older component then does:

| Older component (a release without Group Replication, which does not know the policy name) | Behaviour |
|---|---|
| VTOrc | The detection analysis returns nothing for a shard whose policy it cannot resolve, so it detects and recovers nothing in the keyspace and only logs errors. Upgraded VTOrcs must cover the keyspace. |
| vtctld | ERS, PRS, `InitShardPrimary`, `ChangeTabletType`, `ReparentTablet`, `StartReplication` and `TabletExternallyReparented` return the policy's error. `SetKeyspaceDurabilityPolicy` to an asynchronous policy is still accepted, and cannot be blocked from the new side. |
| vttablet, not primary | Exits at start on the unknown policy; its mysqld stays a group secondary. A migration refuses to start while such a tablet answers (`shard_durability_policy_supported` unset). |
| vttablet, shard primary | Starts without reading the policy, and without a fence. New components never send it a writable RPC (it does not report the group's state), and PRS away from it is refused: liveness, not safety, unless an operator runs `SetWritable`. |

The shard's own policy, the migration source and `shard_durability_policy_supported` come in the same release, so that a vttablet that reports the field resolves both; builds of the prototype from before the migration source are not supported in a keyspace that is being migrated.

The new components also refuse to hand the group to a vttablet that does not run Group Replication:

- The initial promotion of PRS and `InitShardPrimary` require the primary-elect and every tablet that the policy allows as a voter to report `group_replication_enabled` (field 28) and `shard_durability_policy_supported` (field 29) before `InitPrimary`; a vttablet without `--enable-group-replication` refuses `InitPrimary` in a shard whose policy uses Group Replication. Without these checks, such a tablet skipped the bootstrap and made MySQL writable without a group.
- ERS, the PRS primary-elect check and VTOrc's promotion of the group primary (and its choice of a member to move the group primary to) require field 28: a vttablet started without the flag reports its MySQL's group state (field 27), but applies neither the serving invariant nor the fence.

What must be followed by operators, since no component can check it:

- Upgrade vtctld, VTOrc and all vttablets before the first `MigrateReplicationMode`. VTOrc registers nowhere, so the migration cannot see which VTOrcs run; older VTOrcs stop managing the keyspace from step 0 (or misbehave, if they know Group Replication but not the migration source).
- Never downgrade a component that serves a Group Replication keyspace. Migrate the keyspace back to semi-sync first; the rollback ends with the keyspace on the asynchronous policy and no shard policy.
- Never run `SetKeyspaceDurabilityPolicy` from an older vtctld on a Group Replication keyspace: it does not have the guard below. If one did during a migration, the keyspace record has a migration source next to an asynchronous policy: `MigrateReplicationMode` and `SetKeyspaceDurabilityPolicy` say so in a warning, and running `MigrateReplicationMode` to the Group Replication policy again names it in the keyspace record again (or, back to the source policy, ends with the source removed).
- A later release must give any change in the semantics of a Group Replication policy a new policy name, so that this release fails safe on it.

The fields are optional and additive (field 13 of `Shard`, field 13 of `Keyspace`, field 29 of `FullStatus`): older readers skip them, and with no shard having a policy of its own and no migration source, every component behaves as before.

### Where a policy can be set

- **`CreateKeyspace`** (vtctld and legacy vtctl) stores any string, as before: a new keyspace has no shard, and the first promotion of each shard checks the tablets' capabilities (above).
- **`SetKeyspaceDurabilityPolicy`** checks that the policy is registered and, under the keyspace lock, refuses with `FAILED_PRECONDITION`, pointing to `MigrateReplicationMode`, a change that switches between asynchronous replication and Group Replication while a shard of the keyspace is initialized (it had a primary, has a group's voters, incarnation or bootstrap intent, or a policy of its own), and any change while a migration source is set. A keyspace whose shards are not initialized yet, and a change that keeps the replication mode (`semi_sync` to `cross_cell`), are still allowed. A current policy that vtctld does not know, for example one that a newer version wrote, counts as another mode: the change is refused while a shard is initialized, which fails safe, since that policy may run either mode.
- **`MigrateReplicationMode`** writes the shard's own policy at a fixed step of each shard's conversion, and the keyspace record at step 0 and step 8, or at the end of a rollback (see "The shard's policy during a migration"). It only converts between asynchronous replication and Group Replication: a switch between two policies of the mode that the keyspace runs (for example from `semi_sync` to `cross_cell`, or between two Group Replication policies that another build registers) is refused with `FAILED_PRECONDITION` and left to `SetKeyspaceDurabilityPolicy`, so that the migration source is always an asynchronous policy and the voters of a running group are never selected again by the migration. A keyspace without a durability policy is refused too: VTOrc does not manage it, and keeping `none` as its migration source would make VTOrc start to recover its shards. On a shard whose policy is a Group Replication policy and whose group runs, the migration never changes the voters: VTOrc maintains them, and the migration keeps the recorded ones (its step that stores the voters is skipped, and says what its own selection would have been) and goes on with the next shard.

### The migration's pauses and vtgate's buffer

Two migration steps change MySQL under a serving primary in a way that makes MySQL refuse commits for a moment: the bootstrap of the group (forward), and the primary's leave of its group (back). Nothing else does: a voter's join or leave makes a view change on the primary, which delays commits but refuses none, and the switches of semi-sync on the primary refuse nothing. Each of the two steps is a planned pause of the primary, the way PRS's `DemotePrimary` stops serving (`pauseServingLocked`, `go/vt/vttablet/tabletmanager/group_replication_pause.go`):

1. **Notice.** The tablet reports in its health stream that it does not serve (lameduck) while it still serves, for `--group-replication-pause-notice` (100ms). vtgate never sends a request again to a tablet that refused it, even after buffering it, so a write that the primary refused would fail although the same primary serves again a moment later. During the notice vtgate stops sending writes and buffers them; the writes already sent run as before, since MySQL has not changed yet.
2. **Stop serving.** The query service stops serving (`SetServingType` with the reason, as `DemotePrimary` does): new queries get the standard `CLUSTER_EVENT`, and those in flight drain. The tablet keeps its type and primary term. Until the pause ends nothing else makes it serve, such as a refresh after a change of the shard record (`tmState.canServe`).
3. **Change MySQL.** Its refusals fall inside the pause.
4. **Serve again** once MySQL takes writes as the primary (`super_read_only` and `read_only` off, the group's primary if it is a member), which the tablet decides for a group primary whose election ended (Group Replication leaves it read-only), or after `groupReplicationPauseResumeTimeout` (5s): through `SetServingUnlessGroupReplicationNotServing`, so the serving invariant decides (see "Serving invariant"). During a migration the policy is not a group replication policy, and the primary serves; a primary that leaves its group under a group replication policy stays not serving and does not wait.

**How vtgate ends the buffering.** A request that fails with `CLUSTER_EVENT`, or that finds no serving primary while the keyspace event watcher saw the primary stop serving, starts the buffering and marks the shard as waiting for a reparent (`MarkShardNotServing`, `waitForReparent`). vtgate then ends the buffering for a serving primary with a newer primary term, or, once it has seen a not-serving health check of the primary (which clears `waitForReparent`), for the same primary serving again. The notice makes the second case the usual one: vtgate sees the primary stop serving first, and only then starts buffering, after the not-serving health check. A primary that serves again therefore first reports once more that it does not serve (`announceNotServingBeforeResuming`, `go/vt/vttablet/tabletserver/state_manager.go`), right before it serves, whatever made it stop: a migration's pause, the sync loop's serving invariant, `UndoDemotePrimary`. vtgate then drains the buffer as soon as it sees the primary serve, with the same term. `TestBufferingEndsWhenSamePrimaryServesAgain` (`go/vt/vtgate/buffer`) pins this vtgate behaviour; vtgate is unchanged.

**What is left.**
- A request that vtgate sends after the notice ended, without having seen the not-serving health check, is refused and fails after the buffering. The notice makes this unlikely unless vtgate's health stream lags by more than the notice.
- vtgate's health check and its keyspace event watcher learn that the primary stopped serving (the notice) one after the other: the health check drops the primary from the serving tablets first, and the watcher marks the shard not serving when it processes the same health update. A write that vtgate routes in between finds no serving primary while the watcher does not ask for buffering yet; the gateway's retries do not wait, and the write fails at once with `inconsistent state detected, primary is serving but initially found no available tablet` (upstream's `TestInconsistentStateDetectedBuffering` in `go/vt/vtgate` reproduces it). The window is the watcher's processing lag, usually far below a millisecond, and opens at every planned pause of a primary, also a planned reparent with semi-sync. One write of `TestGroupReplicationMigratesShardByShard` failed so in about twenty runs, while a TLA+ checker kept every CPU of the host busy. Only vtgate can close it, for example by letting the retry wait for the watcher.
- If no buffering is in progress when the primary reports again that it does not serve, a request that starts one in the next ~15ms, before the serving health check (the query service opens meanwhile), waits until `--buffer-max-failover-duration`. Writes during the pause, as in any loaded shard, start the buffering before that; only vtgate can close this window.
- The first commit after the pause takes longer: after the leave, up to about 1s for a semi-sync acknowledgement, since Group Replication's stop ends the binlog dump threads and MySQL's semi-sync ack receiver only listens to a reconnected replica from its next poll; after the bootstrap, 0.2–0.9s in the lab.
- vtgate buffers a shard at most once per `--buffer-min-time-between-failovers` (1 minute by default). Each direction has one pause per shard, so a migration that follows another failover of the shard within that time is not buffered.
- **Without `--enable-buffer`,** vtgate fails the writes during the pause, as during a PRS: about 1.35s forward and 3.7s back, plus the notice.

## Recommended topology

- At least three cells with a PRIMARY or REPLICA tablet, under `group_replication_cross_cell`: one voting member per cell, so a group of 3 in three cells. A shard with eligible tablets in fewer than three cells cannot run a group (see "Durability policy and replication mode"). To keep a majority, and so the primary, through two failures, use five cells: a group needs as many cells as voters.
- Additional REPLICA tablets and all RDONLY tablets replicate asynchronously from the group primary, for read scaling. Under `group_replication_cross_cell` this follows from the one-voter-per-cell rule (see "Voters"); a second REPLICA in a cell is a ready replacement when that cell's voter fails.
- `group_replication_paxos_single_leader=ON` and `group_replication_member_expel_timeout=0` are always applied (see Fixed settings).
- Tune flow control so that one slow member does not throttle the primary.
- Async replicas replicate from the primary, as all Vitess replicas do today. Replicating from the local voter would save cross-cell bandwidth, at the cost of lag and repointing when that voter changes; MySQL's `SOURCE_CONNECTION_AUTO_FAILOVER` would handle the repointing.

## Operational notes

- **A VTOrc that dies holds its shard lock until the lock's lease expires.** A shard lock in etcd is a key attached to a lease that the holder keeps alive (`KeepAlive`); `Unlock` revokes the lease. A VTOrc killed during a recovery (SIGKILL, a host crash, an OOM kill) cannot revoke it: the lock outlives the process for up to `--topo-etcd-lease-ttl`, 30s by default, during which every other VTOrc fails to lock the shard on every pass, and no recovery of the shard runs, the bootstrap of a group that lost its majority included. In the S7d chaos scenario with the bootstrapping VTOrc killed, the other VTOrcs failed to lock the shard every second until its lease expired, 30–34s after the kill, and then bootstrapped the group or adopted the one it had bootstrapped (see "Serving invariant, bootstrap intent and the migration's read-only moment" and "Fence check" in `doc/failover-audit/GroupReplication.md`). A VTOrc that exits cleanly (SIGTERM) takes no new lock, waits up to `--shutdown-wait-time` (30s) for its recoveries to release theirs, and so revokes their leases; a bootstrap intent it recorded still fences a bootstrap on another tablet for its two minutes, and the intent's target is chosen again.
- **The trade-off of a shorter lease.** `--topo-etcd-lease-ttl` bounds how long a dead holder blocks the shard, but also how long a live holder may go without renewing its lease: the etcd client renews it about every third of the TTL, and a holder whose renewals stall longer than the TTL (a GC or VM pause, a partition between it and etcd, an etcd leader election) loses the lock while it still acts. Another component can then lock the shard and act concurrently; Vitess only notices at the writes that re-check the lock (`topo.CheckShardLocked`, which renews the lease once, and the compare-and-swap writes of the voters, the incarnation and the bootstrap intent). A TTL of 10s, for example, makes a dead VTOrc block the shard for at most 10s, but needs etcd and the network to answer renewals well within about 3s at all times. The flag applies to every lock and leader election of the process that sets it, so it must be set on every process that locks shards (vtctld and VTOrc among them). It is not changed by this design.

On a shard that never had a primary, a PRS that took the shard lock while VTOrc's bootstrap was running took the initial promotion path and bootstrapped a second group. While no incarnation is recorded, any group counts as the shard's, and the tablets rejoin one on their own: when VTOrc's freshly bootstrapped member leaves or crashes during a voter's join, the join forms a group of its own, another voter joins it, its primary serves and acknowledges writes, and VTOrc's late reply for its own bootstrap records the other incarnation. The initial promotion has the same window. The fix: no join starts while no incarnation is recorded (the tablet's own, VTOrc's `GroupMemberNotOnline`, a new voter's), until the bootstrap is recorded. With it the shard still initializes (`live_init`, `live_init_prs`). A group that `InitPrimary` bootstrapped and whose incarnation write failed was then recorded by nobody, and the shard stayed without a serving primary (`live_init_prs_fail`, `EventuallyServes`); VTOrc now records such a group when it is the only group the shard can have (no live intent, every voter answering, none starting or in another group, its primary holding every voter's transactions), which restores liveness (`live_init_prs_adopt`) and loses no write (`init_orc_adopt`).
  - **A voter write on stale statuses** (`NoLostAck`, `voters_split_slow`, 22 states). VTOrc's write of a voter list used statuses read earlier in the same recovery: a voter dropped as failed came back, was elected, acknowledged a write and failed again before the write, which then left the shard with voters that lacked the write. The compare-and-swap on the list and the incarnation does not see it. The fix: right before the compare-and-swap, VTOrc reads again and refuses the write unless a member of the recorded incarnation is still active with quorum, no voter dropped as unreachable answers or was reached since the selection, and no voter dropped for another reason runs a `START`, is in a foreign incarnation or holds transactions the kept voters lack (`voters_split1`). Each part is needed.
  - **A primary that is not a voter.** A join checks voter status when it starts, and only voter replacement makes a member that is no longer a voter leave; meanwhile Group Replication may elect it, and the serving invariant does not require the primary itself to be a voter, so it can acknowledge a write that no voter holds. In the three-tablet model the only way there is the stale write above, which its re-read refuses; serving only on a voter's MySQL alone does not close it, since a primary promoted while it was a voter keeps serving after the list drops it (`voters_split_nonvoter`). The shipped rules add, as defense in depth: the re-read never drops the group's primary, a PRIMARY tablet that is no longer a voter is fenced, only a voter's MySQL serves, and a non-voter leaves its group on its own (`voters_code`; a failed voter is still replaced, `live_voters`).
- **The voter redesign** (third milestone, before its implementation): one voter per cell, VTOrc's SwapVoter, GrowVoter, GroupPrimaryNotVoter, RemoveVoter and RemoveVoterNoGroup, each one fresh read under the shard lock and a compare-and-swap, with a fourth tablet as the spare, deleted tablet records, hosts that die for good, and liveness. With every rule of the spec (REVISION 2b), the current-design configurations pass: swaps, growth, removals for deleted records, a lost majority recovered by deleting a dead voter's record, and the primary role moved off a non-voter or a deleted voter. Each rule is needed: without P1's election-ended check a swap loses a write (`swap_nosettle`); without P1, RemoveVoter leaves a minority view with the majority of the list (`delete_remove_nop1`); RemoveVoterNoGroup without the deleted record loses a write no deleted voter held (`delete_nogroup_nodel`); a deleted serving primary keeps acknowledging writes until the primary role moves (`delete_primary_window`, the accepted window of `AllowPrimary`); without that move, a deleted voter elected primary leaves the shard without one (`live_delete_active_nomove`). The read-to-write window of about two seconds remains a timing assumption (`swap_split_slow`). The model has one view per incarnation, so P3's "not active" and RemoveVoter's "not in p's view" are implied by P1 there; they guard availability and partial partitions, which it does not model.

Known gaps, found while reviewing and testing the prototype:
- **Three cells, one voter each.** A shard needs eligible tablets in at least three cells, and its group has at most one voter per cell, so a group survives as many failures as a majority of its cells allows: one with three or four cells, two with five. A deployment with two cells, or one that wants two voters in a cell, cannot use Group Replication and keeps semi-sync. A second REPLICA in a cell does not vote; it only replaces the cell's voter.
- During the migration back, the primary re-enables semi-sync only after its group drops below two ONLINE members. That leaves up to one sync interval with neither group nor semi-sync durability. Enabling semi-sync while the group is still active would close this window; it is harmless when an acker is attached.
- A voter that changes to a non-eligible type (RDONLY, DRAINED) stays a voter: VTOrc swaps a voter only when it fails, and removes one only when its tablet record is deleted.
- PRS cannot promote a tablet that is not a voter; it fails and names the voters. Swapping a non-voter in for a voter as part of the reparent is future work.
- Failover time is bounded below by GR's fixed 5s failure detection.
- A join that is in progress when the group it joins loses its majority ends, in MySQL 8.4.11, with the joiner alone in a new group incarnation 9–20s later, or blocks the member for up to a minute (a `STOP` fails meanwhile with errno 3663). Vitess never follows such a group: the tablet's fence check makes it `super_read_only` within about 150ms, and the tablet leaves it (4–6s), but the member then needs another join. After a total loss of the majority, members can stay in ERROR, or not answer status queries, for 5–27s while their communication engine exits, and the group is only bootstrapped again once every voter is readable (see "What an acknowledged commit guarantees"). Under repeated partitions (the S7d chaos scenario) these MySQL delays, not Vitess, bound availability: see "S7d availability" in `doc/failover-audit/GroupReplication.md`. `unreachable_majority_timeout=0`, which avoids the leaves, did not help there and leaves an isolated primary writable. A join that a partition interrupts survives only if the group expels the partitioned member, with the joiner's vote, before the remaining member's `unreachable_majority_timeout`; the joiner's XCom thread blocks 1s at a time connecting to the partitioned member. With 2s the group kept its majority in 19 of 22 such races and in 24 of 26 S7d joins; in the others the remaining member did not see its majority restored, left, and the joiner formed a group of its own, which Vitess does not follow. When the remaining member leaves first, the joiner can end in a view of members that already left (`No donor available`, ERROR), and MySQL's leave then waits for a hard-coded 60s, during which the member's status queries do not return and VTOrc cannot bootstrap; with 2s this happened in 1 of 10 S7d runs. A primary lost within about 0.5s of a voter starting its join loses the majority whatever the timeout: the joiner has not booted yet (0 of 18 races kept at 1s, 2s and 3s).
- The member weight is applied only when a member joins. The members that join during a conversion get MySQL's default weight, since the shard's policy is not a group replication policy yet; they get the policy's weight when they rejoin. With the built-in policies every voter has the default weight anyway.
- A bootstrap whose reply VTOrc does not get is adopted once VTOrc reaches the target again. While VTOrc cannot reach it, the tablet trusts the group it bootstrapped for `groupReplicationBootstrapGrace` (1 minute) and then leaves it; the intent fences a bootstrap on another tablet for two minutes, which only matters when the voters' GTID sets are equal (the candidate is otherwise the same), or when the candidate's mysqld restarted after VTOrc chose it and the bootstrap RPC failed without a definitive refusal, for example because it reached the tablet while mysqld was still down, until the candidate answers again, in no group and without a `START` (VTOrc then sends it the intent's bootstrap again, which it refuses definitively; a definitive refusal withdraws the intent at once; see "Bootstrap intent"). A VTOrc killed during a recovery holds the shard lock until its topology lease expires (see "Operational notes").
- A serving primary whose view shrinks to a minority of the voters because voters leave cleanly keeps committing until the fence check notices, within `groupReplicationFenceCheckInterval` (150ms) plus a query, rather than the sync loop's `--group-replication-sync-interval`: in G11, MySQL was fenced 0.02–0.11s after its view of one, and 4–20 writes were committed on a single voter, against 32–84 over 0.25–0.81s before (see "Fence check" in the audit). MySQL itself cannot fence this case: the primary was writable before its view shrank. Every other primary that Group Replication elects stays read-only now that the member action `mysql_disable_super_read_only_if_primary` is disabled (see "Only Vitess makes MySQL writable"): a stray group of one that a join forms is not writable at all (it was for 0.01–0.15s with the fence check alone, in G12 and S7d, and for 4.6–5.7s before the check), and neither is a REPLICA whose MySQL the group's own election makes the primary of a recorded view without the voter majority, which took the writes of clients that wrote to it directly, since the fence check does not watch a REPLICA outside of its joins. The check's read waits for its 2s timeout while the tablet's own `STOP GROUP_REPLICATION` runs, since MySQL does not return the view id then either; MySQL is `super_read_only` during a leave, so nothing is missed. The fence check relies on the tablet's last reads of the shard record and the durability policy; it does not fence a stray group of a voter whose tablet has never read the shard record, nor a group of its own that MySQL's own auto-rejoin forms (`--group-replication-autorejoin-tries`, 0 by default) more than 30s after the tablet's last join: both stay read-only by MySQL's configuration, and the reconcile loop leaves them within its interval.
- vtgate buffers the migration's pauses only with `--enable-buffer`, and at most once per `--buffer-min-time-between-failovers`; a buffering that starts in the ~15ms between the primary's last not-serving health check and its serving one, when none was in progress, lasts until `--buffer-max-failover-duration` (see "The migration's pauses and vtgate's buffer"). Only vtgate could close that window, by not waiting for a reparent once its keyspace event watcher saw the primary stop serving.
- VTOrc moves a group primary out of a cell whose topology server is down only when its own vantage point cannot reach that server, and only after it has observed the member as the group primary through the member's vttablet (the analysis needs a valid check of it). Under an asymmetric partition, VTOrcs of different cells may disagree about which cells answer; the shard lock serializes their moves and each one re-reads the group under the lock, but the one-minute hold against moving back is per VTOrc. A group primary whose vttablet does not answer either is left to the ERS fallback after `--group-replication-failover-grace-period`.
- While a cell's topology server hangs, VTOrc's main loop is blocked by each topology refresh for `--topo-information-refresh-duration`, so discovery and analysis run at that period (3s in the chaos tests) rather than every second. In G9b this put the detection of `GroupPrimaryNotInTopo` 10s after the election; the move itself took 5s.
- **What an acknowledgement covers.** A group acknowledges a commit once a majority *accepted* it in XCom, in memory. A transaction is lost only if the primary's disk is lost and, at the same time, the majority crashes before any other member received it; Vitess then stops rather than bootstrap without it (VTOrc bootstraps only when every voter is reachable). Semi-sync has a comparable exposure (its acker's relay log). `--group-replication-consistency=AFTER` closes it, at the cost of commit latency: the primary acknowledges only once every member applied the transaction.
- **A deposed primary that has not learned of its expulsion.** A primary that is paused or cut off and misses the view that removes it still sees itself as the primary of a full view: its tablet stays PRIMARY and MySQL `read_only=OFF` until it learns of the expulsion. It cannot commit (certification blocks, then rolls back with errno 3100), so no write is lost or diverges, but it serves reads until vtgate sees the new primary. Measured: 25–33ms in S2 (pause), 5.2s once in S7c (a flapping network), with 5 reads served between the election and the topology change.
- **The relay log applier.** The bootstrap candidate must apply the transactions that it only received; if its applier cannot apply them, it refuses every bootstrap and VTOrc keeps choosing it, and the shard needs an operator. Not seen in the lab or in chaos.
- **The token check fails open.** A bootstrap RPC checks that its intent is still the shard's, but skips the check when the tablet's topology server does not answer within a second, and bootstraps as before the check: a bootstrap that the topology keeps from running would cost availability too. The model's `stale_rpc_timeout` shows the exposure: a stale RPC that also misses the check can bootstrap a second group.
- **A bootstrap intent fences for two minutes.** When a bootstrap RPC fails without a definitive refusal and its target then stops answering, or runs a `START`, the intent keeps the other voters from bootstrapping until it expires. While the target answers, VTOrc re-probes it on every pass, each pass waiting up to `--wait-replicas-timeout` (30s) under the shard lock if the tablet does not answer the RPC.
- **Timing assumption of the voter changes.** VTOrc decides a change of the voters on one read, 2s per tablet at most, and writes it right after: the model assumes that the read and the compare-and-swap do not span a stall long enough for a voter to come back, be elected and fail again. The settled check (P1) replaces the earlier assumption that the voter replacement grace period outlasts the group's election.
- **`InitPrimary` makes MySQL writable before the tablet serves.** A client that writes to MySQL directly, bypassing vtgate, during the initial promotion can lose that write if the promotion then fails (`init_direct` in the model). vtgate's writes are not affected.
- **A replaced voter is repaired as an asynchronous replica.** VTOrc gives an unreachable voter's seat to a spare of its cell after `--group-replication-voter-replacement-grace-period` (SwapVoter). When the old voter comes back, it is not a voter, and VTOrc's asynchronous repair configures replication from the primary on it; it becomes a voter again only as the spare of a later swap (S8 and S10 of the chaos round on the fixes: the old primary, back after 73–78s, replicated asynchronously for about 0.1s). Harmless in those runs; part of the voter-replacement review.
- **What VTOrc keeps about a deleted voter does not survive a VTOrc restart.** VTOrc keeps the address, `server_uuid` and last-seen time of a listed voter whose tablet record was deleted (`vitess_deleted_group_voter`), so that it can tell a dead voter from a running one before it removes it. Its backend database is rebuilt at startup, so a VTOrc that never saw that voter treats it as not down and never removes it: the shard fails closed, with `GroupVoterRecordDeleted`, until the operator stops the voter's vttablet and MySQL or restarts its vttablet (which re-creates the record), or until a VTOrc that saw it acts.
