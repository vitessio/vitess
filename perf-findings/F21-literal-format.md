# F21-literal-format: string literal formatting in sqlparser

## Verdict
**Do it.** This is a tiny change with no behaviour change. Output is byte-identical: it uses the same `encodeBytesSQL*` escaping logic, just the `*strings.Builder` variant. It removes 2-3 allocations per string literal. It also composes with F03: F03's `*strings.Builder` fast path does not match `*TrackedBuffer`, so without F21, F03 leaves this path on its slower generic-BinWriter branch.

## Finding re-verification (HEAD, this worktree)
- `ast_format.go:1573` and `ast_format_fast.go:2025` (`Literal.Format` / `FormatFast`, case `StrVal`) contain:
  `sqltypes.MakeTrusted(sqltypes.VarChar, node.Bytes()).EncodeSQL(buf)`.
  - `node.Bytes()` (`ast_funcs.go:694`) is `[]byte(node.Val)`, which is one full copy.
  - `EncodeSQL(BinWriter)` then calls `encodeBytesSQL` (`value.go`). That allocates a new `&bytes2.Buffer{}` with zero capacity, grows it about log n times, and then `b.Write`s it into the TrackedBuffer.
- `TrackedBuffer` embeds `*strings.Builder` (`tracked_buffer.go:39`). This means `buf.Builder` is directly usable by `Value.EncodeSQLStringBuilder` → `encodeBytesSQLStringBuilder`. That code is byte-for-byte the same algorithm as `encodeBytesSQLBytes2`: a byte loop with the `\%`/`\_` rule and the same `SQLEncodeMap`.
- The rune-based `BufEncodeStringSQL` was deliberately **not** used. It turns invalid UTF-8 bytes into U+FFFD.
- HexVal/HexNum/BitNum/Int/Float/Date literals already use `WriteString` in FormatFast and `%#s` in Format. They need no change.

## Generator
- `ast_format_fast.go` is generated by `go/tools/astfmtgen`. The directive is `//go:generate go run ../../tools/astfmtgen vitess.io/vitess/go/vt/sqlparser/...` in `go/vt/sqlparser/generate.go`.
- The generator only rewrites `buf.astPrintf(...)` and `buf.literal(...)` calls. Every other statement is copied verbatim.
- I edited `ast_format.go` and re-ran the generator from `go/vt/sqlparser`. The generated diff is exactly the one mirrored line, so it is clean.

## Change (prototype, uncommitted in worktree)
- `tracked_buffer.go`: a new helper was added:
  ```go
  func (buf *TrackedBuffer) writeStringLiteral(val string) {
      sqltypes.MakeTrusted(sqltypes.VarChar, hack.StringBytes(val)).EncodeSQLStringBuilder(buf.Builder)
  }
  ```
- `ast_format.go` and the regenerated `ast_format_fast.go` call `buf.writeStringLiteral(node.Val)`.
- `tracked_buffer_test.go`: new `TestStringLiteralFormatEquivalence`.
  - It checks both `String(lit)` (FormatFast) and `Format` against the old oracle `MakeTrusted(VarChar, []byte(val)).EncodeSQL(&bytes.Buffer{})`.
  - Inputs: every string of 0-2 bytes (65,793 cases), hand-picked edge cases (`\%`, `\_`, `\\%`, trailing `\`, control chars, invalid UTF-8, CJK), and 20k random strings biased toward special bytes. It passes with and without F03 applied.
- `literal_format_bench_test.go`: new `BenchmarkFormatStringLiteral`, covering String, Format and Redact on 10 B, 1 KiB, 5x10 B and 5x240 B literals, plus a no-literal control.
- Size: about 12 LOC of production code in 3 files (one generated), about 55 LOC of tests and 65 LOC of benchmark.

## Benchmarks
All numbers are measured, from `sqlparser.String`. Four test binaries ran interleaved, n=10, 100 ms each, on a shared noisy box.

Variants:
- **old**: HEAD
- **new**: F21
- **oldF03**: HEAD + F03 patch
- **newF03**: F21 + F03 patch

Findings from these numbers:
- F21 alone removes about 2.5-3 allocations per string literal: the `[]byte` copy, the `bytes2.Buffer` header escaping through the interface, and its growth steps.
- With F03 applied, F21 still removes the final copy per literal. It also routes onto F03's `*strings.Builder` fast path, which F03's type switch cannot reach because the dynamic type is `*TrackedBuffer`. The effect is 1.88 → 1.41 µs at 1 KiB and 882 → 681 ns at 5x10 B.
- The per-literal numbers match the earlier scratch run: 240 B went from 932 ns/11 allocs to 763 ns/7 allocs.
- `Format` (the non-fast path) shows the same allocation deltas.
- **RedactSQLQuery: no change.** Allocation counts are identical, and time is noise at ±40-80%. This is expected: it normalizes every string literal to a bind variable before calling `String`, so no StrVal literal reaches the formatter.

## End-to-end relevance (estimated, not measured)
- The vtgate OLTP path with normalization on (the default) turns most string literals into bind vars before formatting. There, F21 only affects literals the normalizer skips, such as DDL defaults and comments or some SET and ORDER/GROUP BY literals, so the effect is small.
- The benefit is real for:
  - schemadiff, online DDL and declarative schema work, where CREATE TABLE has many `DEFAULT '...'` / `COMMENT '...'` literals and is formatted repeatedly;
  - deployments with normalization disabled;
  - vreplication and vtctld code that builds queries from ASTs holding literals;
  - query logging with `sqlparser.String`;
  - vtexplain.
- Expect a few percent of the formatting cost there, not a headline number. The main value is allocation and GC reduction, at essentially zero risk.

## Gotchas
- `hack.StringBytes` aliases `node.Val`. That is safe because the encoder only reads the slice and does not retain it. The `Value` is a stack temporary.
- `buf.Builder` must be non-nil. It always is for `NewTrackedBuffer`, and `WriteString` would already panic otherwise.
- Do not switch to `BufEncodeStringSQL`: it changes the output for invalid UTF-8 (U+FFFD).
- Release compatibility: output is byte-identical and the helper is unexported, so there is no API change.
- Coordination with F03:
  - Independent of F03 and composes with it.
  - Alternatively, F03 could add a `case interface{ WriteString(string) (int, error) }` branch to its type switch. That would help other BinWriter callers, but it would still leave the `Bytes()` copy.
- Side note (not changed): `normalizer.go:505-535` calls `lit.Bytes()` 2-3 times per HexNum/HexVal/BitNum literal, which means redundant copies. StrVal/IntVal there need their copy because the Value is retained in the bind vars. This is minor and rare.
